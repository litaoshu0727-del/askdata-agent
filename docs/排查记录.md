# AskData 电商数据集接入排查记录

分三批。前两批是踩坑：三个来自把 Demo 数据集从 2 张表 9 个字段换成 11 张表 81 个字段，
三个来自加多轮追问场景——五轮对话第一次跑下来错了三轮。
六个的共同点是：**链路全程不报错，退出码是 0，只是结果悄悄变差或者提前结束**。

第三批不同：不解决具体 bug，而是建立度量——
把"感觉准了"变成一个可证伪的数字，顺便发现前六个问题只是撞见的那部分。

记录顺序按实际排查顺序，包含走错的方向。

# 第一批：单轮 Text2SQL

---

## 问题一：精排名额没随 Schema 规模放大，导致静默漏召回

### 现象

跑第一条测试 Query：

```bash
python -m askdata_pipeline.ecommerce_demo --query "销售额最高的三个店铺是哪些"
```

SQL 能跑、结果也对，但返回的是店铺 ID 而不是店铺名：

```sql
SELECT shop_id, SUM(gmv) AS total_gmv FROM dws_shop_daily
GROUP BY shop_id ORDER BY total_gmv DESC LIMIT 3;
```

```json
{"shop_id": 2015, "total_gmv": 1164408.98}
```

模型在 CoT 里把原因写出来了：

> 若需要返回店铺名称，因 Schema 未提供 dim_shop 的店铺名称字段，
> 无法通过 shop_id 关联补充，当前仅能返回 shop_id

模型没幻觉，它是**诚实地报告了自己拿到的 Schema 里没有这个字段**。
问题出在它上游。

### 排查

打印检索阶段实际命中的字段，一共只有 6 个：

```
dim_shop        : shop_type, shop_id
dws_shop_daily  : gmv, buyer_count, order_count, shop_id
```

库里有 81 个字段，只召回 6 个，`shop_name` 不在里面。

### 走错的第一步

第一反应是元数据写得不够好，于是给 `dim_shop.shop_name` 加了别名和关键词文本：

```python
"aliases": ["店铺名称", "店铺名", "商家名称", "店名", "店铺"],
"keyword_text": "shop_name 店铺名称 ... 哪些店铺 哪个店铺 店铺排行 top店铺",
```

重跑，**`shop_name` 依然没被召回**。说明瓶颈不在"能不能被检索到"，
而在"有没有名额"。

### 根因

`schema_retrieval/hybrid_schema_retrieval_service.py`：

```python
def _calculate_rerank_top_n(self, keyword_count, candidate_count):
    dynamic_top_n = keyword_count * self.config.rerank_top_multiplier
    top_n = max(self.config.rerank_min_top_n,
                min(dynamic_top_n, self.config.rerank_max_top_n))
    return min(top_n, candidate_count)
```

默认参数 `rerank_top_multiplier=2`、`rerank_min_top_n=2`。
这条 Query 抽出 2 个关键词（销售额、店铺），于是：

```
rerank_top_n = 2 × 2 = 4
```

**精排只保留 4 个字段**。再加上 `include_join_columns=True` 补进来的关联键，
最终进入 SchemaGraph 的就是那 6 个。

这套参数是给原始 trade 库调的——2 张表 9 个字段，留 4 个名额绰绰有余。
换到 81 个字段的库上，光金额类字段就有 9 个，4 个名额连候选都装不下。

### 修复

把检索配置按数据集拆开，`askdata_pipeline/text2sql_pipeline.py`：

```python
def _build_retrieval_config(self) -> HybridSchemaRetrievalConfig:
    if dataset == "ecommerce":
        return HybridSchemaRetrievalConfig(
            per_keyword_top_k=30,
            rrf_config=RRFFusionConfig(final_top_k=60, max_fused_top_k=80, ...),
            rerank_top_multiplier=6,
            rerank_min_top_n=10,
            rerank_max_top_n=30,
        )
    # trade 库字段少，保持原有参数
```

### 验证

```
dim_shop: shop_name, shop_type, shop_id     ← shop_name 进来了
```

```sql
SELECT dim_shop.shop_name, SUM(dws_shop_daily.gmv) AS total_gmv
FROM dws_shop_daily
JOIN dim_shop ON dws_shop_daily.shop_id = dim_shop.shop_id
GROUP BY dws_shop_daily.shop_id, dim_shop.shop_name
ORDER BY total_gmv DESC LIMIT 3;
```

```json
{"shop_name": "臻品自营店15", "total_gmv": 1164408.98}
```

### 经验

- **召回/精排的 top_k 是随 Schema 规模变化的超参，不是常量。**
  Demo 库调好的参数搬到生产库上大概率不够用。
- **这类失败是静默的。** 没有异常、没有告警，只是少给了几个字段，
  最后表现为模型说"Schema 里没有这个字段"——很容易被误判成模型能力不行。
- 排查顺序值得记住：先看**检索实际召回了什么**，再看元数据写得好不好。
  召回结果为空和召回名额不够，是两个完全不同的问题。

## 问题二：CoT 解析器对标点敏感，导致链路静默中断

### 现象

```bash
python -m askdata_pipeline.ecommerce_demo --query "客单价最高的10个用户是谁"
```

CoT 四元组输出得非常漂亮，"客单价"也正确映射到了 `avg_order_amount`：

```
步骤1：
(
  数据库: ecommerce_db,
  处理对象: dws_user_summary.avg_order_amount；dim_user.user_name；关联关系：...,
  操作指令: 先确定"客单价"对应字段为dws_user_summary.avg_order_amount；...
            最后返回对应用户的user_id、user_name和avg_order_amount。
  输出目标: user_id, user_name, avg_order_amount
)
```

然后就没有然后了。**没有生成 SQL，没有执行结果，退出码 0。**

### 排查

`text2sql_pipeline.run()` 里 SQL 生成挂在这个循环上：

```python
for cot_step in cot_result.steps:
    ...
```

`cot_result.steps` 是空列表，循环体一次都没进，直接返回了一个
`step_logs=[]` 的结果。`parse_steps()` 解析失败了。

### 根因

`cot_planning/cot_planner.py` 的正则：

```python
r"操作指令:\s*(?P<operation_instruction>.*?)\s*,\s*"
r"输出目标:\s*(?P<output_target>.*?)\s*"
```

**要求"操作指令"和"输出目标"之间必须有一个半角逗号。**

对比两次输出就看出来了：

| | 操作指令结尾 | 解析 |
|---|---|---|
| 能跑通的那几条 | `...最后获取对应的interest_rate,` | ✅ |
| 这一条 | `...和avg_order_amount。` + 换行 | ❌ |

模型这次在句尾用了句号，没加逗号。仅此而已，整个四元组就匹配不上。

而 `parse_steps` 的设计是**静默失败**：

```python
"""解析失败时不影响主流程，直接返回空列表。"""
```

初衷是不让解析问题打断主流程，代价是这类 bug 完全没有痕迹。

### 修复

不再依赖分隔符，改用**下一个标签名当锚点**，中间的逗号有就吃掉、没有也不影响；
顺便兼容全角冒号和全角逗号：

```python
pattern = re.compile(
    r"步骤(?P<step_no>\d+)[：:]\s*"
    r"\(\s*"
    r"数据库[：:]\s*(?P<database>.*?)\s*[,，]?\s*"
    r"处理对象[：:]\s*(?P<processing_objects>.*?)\s*[,，]?\s*"
    r"操作指令[：:]\s*(?P<operation_instruction>.*?)\s*[,，]?\s*"
    r"输出目标[：:]\s*(?P<output_target>.*?)\s*"
    r"\)",
    re.S,
)
```

### 验证

四种变体全部解析成功：

```
✅ 句号结尾（之前失败的真实输出）: 解析出 1 个步骤
✅ 半角逗号（原本就支持）      : 解析出 1 个步骤
✅ 全角逗号                    : 解析出 1 个步骤
✅ 多步骤                      : 解析出 2 个步骤
```

重跑原 Query：

```sql
SELECT dws_user_summary.user_id, dim_user.user_name, dws_user_summary.avg_order_amount
FROM dws_user_summary
JOIN dim_user ON dws_user_summary.user_id = dim_user.user_id
ORDER BY dws_user_summary.avg_order_amount DESC LIMIT 10;
```

返回 10 行，客单价最高 33397.19。

### 经验

- **解析 LLM 的结构化输出，要锚定"标签"而不是"分隔符"。**
  标签是你在 Prompt 里明确要求的，模型会照做；
  分隔符属于标点习惯，同一个模型不同次调用都可能不一样。
- **静默失败比抛异常危险得多。** 这个 bug 能跑通全链路、退出码 0、
  CoT 看着完全正常，只有盯着输出才发现少了两段。
  如果它发生在线上，就是一个"偶发不出结果"的幽灵问题。
- 类似的脆弱点还有：全角半角、中英文引号、Markdown 代码块包裹、
  模型在 JSON 前后加解释性文字。都应该按锚点解析 + 容错。

## 问题三：.env 自动加载污染了单元测试

### 现象

给项目加上 `.env` 支持之后：

```bash
python -m unittest discover -s tests
# Ran 12 tests in 36.142s      ← 之前是 0.074s
```

测试还是全过，但慢了 500 倍。

### 根因

`llm_config.resolve_chat_provider()` 会自动加载 `.env`，于是测试进程里：

1. 读到了真实的 `DEEPSEEK_API_KEY`
   → `dynamic_service._build_model_client()` 返回真实客户端，**测试开始打真实 API**
2. 读到了 `ASKDATA_LOCAL_MODELS=1`
   → `conversation._build_default_reranker()` 加载 1.1GB 的 bge-reranker

单元测试因此变成了：依赖网络、消耗 API 额度、在没有 `.env` 的机器上行为不一致。
**测试失去了封闭性。**

### 修复

给自动加载留一个逃生舱，`llm_config.py`：

```python
def ensure_dotenv_loaded() -> None:
    ...
    if os.getenv("ASKDATA_DISABLE_DOTENV", "").strip().lower() in {"1", "true", "yes", "on"}:
        return
    load_dotenv()
```

两个测试文件在导入项目模块之前先隔离环境：

```python
os.environ["ASKDATA_DISABLE_DOTENV"] = "1"
for _key in ("DEEPSEEK_API_KEY", "DASHSCOPE_API_KEY",
             "DASHSCOPE_WORKSPACE_ID", "ASKDATA_LOCAL_MODELS"):
    os.environ.pop(_key, None)
```

### 修复过程中的小插曲

第一次把这段代码插到了文件最开头，直接报错：

```
SyntaxError: from __future__ imports must occur at the beginning of the file
```

`from __future__ import annotations` 必须是文件里第一条语句（docstring 除外）。
隔离代码要放在它**后面**、在导入项目模块**前面**。

### 验证

```
Ran 12 tests in 0.074s
OK
```

### 经验

- **任何"自动加载配置"的机制都会破坏测试封闭性**，
  `.env`、全局配置文件、用户级配置都算。加的时候就要同时提供关闭开关。
- 判断标准很简单：**这个测试在一台没有任何配置的新机器上，行为应该完全一样。**
- 测试变慢往往不只是慢——它通常是"测试开始依赖外部世界"的第一个信号。

# 第二批：多轮追问场景

前三个问题是做单轮 Text2SQL 时踩到的。后来加了一个五轮追问的 Demo，
第一次跑下来 **5 轮里错了 3 轮**——而且同样，一次都没报错。

多轮的难点不在 SQL，在**指代消解**：用户第二句说「它们的退款金额呢」，
「它们」指的是上一轮 SQL 查出来的那三家店铺，这个信息不在当前 Query 里。

---

## 问题四：代词被当成了检索关键词

### 现象

第二轮追问：

```text
轮次 2　用户：它们的退款金额分别是多少

检索关键词   它们，退款金额
SQL         SELECT shop_id, SUM(refund_amount) AS total_refund_amount
            FROM dws_shop_daily GROUP BY shop_id;
执行         返回 15 行
```

SQL 语法正确、执行成功、返回了数据。但它查的是**全部 15 家店铺**，
而用户问的是上一轮那 3 家。结果多了 12 行，没有任何报错。

### 排查

关键词里赫然躺着「它们」。代词没有任何检索价值，
而真正该进检索的三个店铺名一个都没有。

翻到 `text2sql_pipeline.run()`：

```python
resolved_keywords = keywords or self.keyword_extractor.extract(query)

contextual_query = query
if conversation_context.strip():
    contextual_query = (
        f"以下是与当前问题相关的会话记忆：\n{conversation_context}\n\n"
        f"当前用户问题：{query}"
    )
```

### 根因

**会话记忆拼进了 `contextual_query`，但关键词抽取用的是原始 `query`。**

也就是说，检索和 CoT 都能看到上下文，只有最前面的关键词抽取是「瞎」的。
而关键词抽取决定了 BM25 召回哪些字段——这一步抽歪了，后面全是错的。

再往深想一层：把 `contextual_query` 直接喂给关键词抽取也不对。
整段会话历史送进去，会抽出一堆上一轮的历史关键词，
反而把当前这轮真正要查的字段淹掉。

**指代消解需要的是改写，不是拼接。**

### 修复

新增 [query_rewriter.py](../askdata_pipeline/query_rewriter.py)，
把指代消解拆成显式的一步，放在关键词抽取**之前**：

```text
用户：它们的退款金额分别是多少
  ↓ 指代消解
销售额最高的三个店铺"臻品自营店15""优选旗舰店1""旗舰旗舰店7"的退款金额分别是多少
  ↓ 关键词抽取
销售额，店铺，臻品自营店15，优选旗舰店1，旗舰旗舰店7，退款金额
```

只有检测到指代词（它们、这些、刚才、上述……）才调模型，
自包含的问题直接短路，不浪费一次调用。

### 验证

```sql
SELECT dim_shop.shop_name, SUM(dws_shop_daily.refund_amount) AS refund_amount_total
FROM dim_shop JOIN dws_shop_daily ON dim_shop.shop_id = dws_shop_daily.shop_id
WHERE dim_shop.shop_name IN ('臻品自营店15', '优选旗舰店1', '旗舰旗舰店7')
GROUP BY dim_shop.shop_id, dim_shop.shop_name;
```

返回 3 行，正是上一轮那三家。

### 经验

- **「把上下文拼进 Prompt」不等于「模型会用上下文」。**
  要确认这段上下文到底流到了链路的哪几个环节——
  这次就是漏了最前面、也最关键的那一环。
- **指代消解是独立的一步，不是 CoT 的副产品。**
  检索增强里这一步有专门的名字叫 query rewriting，
  它必须发生在任何「基于 Query 做召回」的动作之前。
- 多轮链路要逐环节问一句：这一环拿到的是原始 Query 还是改写后的 Query？

## 问题五：模型从店铺名里抠出数字，当成了 ID

### 现象

第五轮追问「帮我查一下这些店铺的买家数」，生成的 SQL 是：

```sql
SELECT fact_order.shop_id, COUNT(DISTINCT fact_order.user_id) AS buyer_count
FROM fact_order
WHERE fact_order.shop_id IN (15, 1, 7)
GROUP BY fact_order.shop_id;
```

```text
执行   返回 0 行
```

### 排查

`15, 1, 7` 这三个数字是哪来的？对照上一轮的结果：

| 店铺名 | 模型推断的 ID | 真实 shop_id |
|---|---|---|
| 臻品自营店**15** | 15 | 2015 |
| 优选旗舰店**1** | 1 | 2001 |
| 旗舰旗舰店**7** | 7 | 2007 |

模型把店铺名**末尾的数字**当成了 ID。

### 根因

模型需要一个过滤条件，但上下文里只有店铺名、没有 `shop_id`。
于是它「推理」出了一个——而且推理过程看起来完全合理：
店铺叫「臻品自营店15」，那它是第 15 家店，ID 大概就是 15。

**这不是随机幻觉，是有迹可循的错误推断。**这类错误比胡编更危险，
因为它看起来有理有据，人扫一眼 SQL 甚至不会觉得可疑。

而且它**返回 0 行、不报错**——又是一个静默失败。

### 修复

两层防护。

一是在改写 Prompt 里写死这条约束：

```text
3. 绝对不要凭空推断任何 ID。比如店铺名叫"臻品自营店15"，不代表它的 ID 是 15。
```

同时要求改写后的问题必须使用历史结果里出现过的**原始值**，
这样模型手上就有可直接用于过滤的店铺名，不需要去猜 ID。

二是新增 `EMPTY_RESULT_SET` 降级码：

```python
if execution_result.success and not execution_result.rows:
    emit(Codes.EMPTY_RESULT_SET,
         "SQL 执行成功但返回 0 行，请检查筛选条件是否正确"
         "（多轮追问中常见于凭空推断的 ID）", ...)
```

### 验证

```sql
WHERE dim_shop.shop_name IN ('臻品自营店15', '优选旗舰店1', '旗舰旗舰店7')
```

返回 3 行。

### 经验

- **幻觉常常不是凭空的，是「看起来合理的推断」。**
  防它的办法不是让模型「更小心」，而是让它**不需要推断**——
  把可直接使用的原始值放到它手上。
- **0 行结果要当成可疑信号，不是正常结果。**
  SQL 跑通、退出码 0、返回空集，这三件事同时成立时最容易被放过。
- Prompt 里的禁止项要**举具体的反例**。写「不要推断 ID」不如写
  「店铺名叫"臻品自营店15"，不代表它的 ID 是 15」。

## 问题六：data_qa 看不见 Schema，答不出指标口径

### 现象

第四轮问「客单价这个指标是怎么算的」，路由判对了（`data_qa`，不查库），
但答案是：

> 当前上下文中**没有提供"客单价"的明确定义或计算口径**，
> 因此我不能确定 `ecommerce_db` 里客单价具体怎么算。

而 `dws_user_summary.avg_order_amount` 的业务元数据里写得清清楚楚：

```python
"aliases": ["客单价", "平均订单金额", "笔单价", "平均客单价"],
"description": "该用户的平均订单金额，也就是通常说的客单价。",
```

### 根因

`ModelDataQAClient` 的 Prompt 里只有一样东西：

```python
context_text = context.to_prompt_context()   # 只有会话记忆
```

而口径信息在 `business_meta` 里，那是 Text2SQL 链路才接触的东西。

**路由把这类问题分给了 data_qa，却没把 data_qa 需要的知识一起分过去。**
分支有责任、但没有对应的信息，只能诚实地说「我不知道」。

### 修复

`build_metric_glossary()` 把 `business_meta` 压成一份指标口径表：

```text
- dws_user_summary.avg_order_amount（业务上也叫：客单价、平均订单金额、笔单价）：
  该用户的平均订单金额，也就是通常说的客单价。
```

只取字段名、别名和业务含义，不带样例值和索引文本，控制住 Prompt 体积，
再由 `DynamicAskDataService` 在构造时传给 `data_qa`。

### 验证

```text
"客单价"在给定指标口径表中对应的是：
- 表：dws_user_summary
- 字段：avg_order_amount
- 常用叫法：客单价、平均订单金额、笔单价、平均客单价
```

### 经验

- **路由分流时，要连同该分支需要的上下文一起分过去。**
  否则分支会「有责无权」——判断是对的，但没有能力完成。
- 这个问题和问题四是同一类：**信息在系统里存在，只是没流到需要它的那一环。**
  链路越长、分支越多，越容易出现这种断点。
- 元数据的价值不止于检索。同一份 `business_meta`，
  在 Text2SQL 链路里用来召回字段，在问答链路里用来解释口径。

# 第三批：建立度量

前两批是"踩坑 → 修复"。这一批性质不同：**不解决具体 bug，而是解决"没法知道有没有 bug"。**

前面六个问题全是撞见的——改完精排参数跑一条 Query 看对不对，修完解析器再跑一条看对不对。
其中 SQL 库名前缀那个，同一道题连过两轮、第三轮才挂。**手跑单条 Query 有 2/3 的概率看不见它。**

---

## 10 题的 100% 是假象

第一版评测集只有 10 题，跑出来 10/10。看着很好，其实说明题目太简单、已经没有区分度——
无论精排参数怎么调、换哪个模型、把元数据别名删掉一半，分数都会是 100%。

**一个测不出差异的评测集，和没有评测集区别不大。**

扩到 50 题（加了跨表多跳、嵌套聚合、时间窗口、陷阱题四组），分数立刻掉下来：

```text
Schema 召回率     57/67    85%     检索环节
执行准确率        33/42    79%     生成环节
陷阱题诚实率       5/5    100%     可靠性
端到端准确率      38/50     76%    整条链路

失败构成：SQL 报错 3 题，结果不符 9 题
```

76% 才是这条链路的真实水平。

---

## 发现一：检索偏向"指标字段"，系统性漏掉名称与枚举

12 道失败题里有 7 处漏召回。把它们列出来，模式非常清楚——**没有一个是指标字段**：

| 漏掉的字段 | 类型 | 后果 |
|---|---|---|
| `dim_user.user_name` ×2 | 输出维度 | 问"哪个用户"，返回了 `user_id` |
| `dim_shop.shop_name` | 输出维度 | 问"哪家店"，返回了 `shop_id` |
| `fact_order.channel` | 筛选枚举 | 筛不了"直播间" |
| `fact_user_behavior.behavior_type` | 筛选枚举 | 筛不了"加购" |
| `fact_order_item.quantity` | 计量字段 | "销量"算成了订单行数 |
| `dim_product.list_price` | 价格 | 模型以为库里根本没有标价 |

问题里**明确出现的指标词**（销售额、退款金额、客单价）召回得很好；
但"哪家店""哪个用户"这种**隐含要的名称字段**，以及筛选用的**枚举字段**，系统性地漏。

E36 / E38 / E43 三道题是同一个病：问"是哪家 / 是谁"，全都返回了 ID。

```sql
-- E38「单笔实付金额最高的那笔订单是哪个用户下的」
SELECT user_id FROM fact_order ORDER BY pay_amount DESC LIMIT 1;
                ^^^^^^^ 问的是"哪个用户"，答的是一串数字
```

这是个**可归因、可修复**的模式，不是随机失败。指标词本身就带语义、容易被向量召回；
而"名称"这类需求是隐含的——Query 里根本没有"店铺名称"四个字，
它得靠元数据里那句"当用户问哪些店铺时应该输出本字段"才能被捞上来。

---

## 发现二：又一个退出码 0 的假答案

E18「通过直播间下单的订单有多少笔」，`channel` 没被召回，模型生成了：

```sql
SELECT COUNT(order_id) FROM fact_order WHERE 1=0;
```

语法正确、执行成功、返回 0。**又是一个退出码 0 的静默失败。**

模型的处境其实很合理：它需要按渠道筛，但拿到的 Schema 里没有渠道字段，
于是写了一个恒假条件——这是"诚实"的表现，只是表现形式是一个看起来正常的 0。

好在第二批加的 `EMPTY_RESULT_SET` 告警接住了它。降级记录里正好 1 题次，就是这道。
**上一批装的探针，在这一批派上了用场。**

---

## 发现三：模型的拒答被当成 SQL 执行了

E39「平均标价最高的一级类目是哪个」，`dim_product.list_price` 没被召回。
模型看着手上残缺的 Schema，做出了正确判断：

> 当前Schema无法支撑该查询：dim_product表中缺少商品标价字段，仅有cost_price成本价，
> fact_order_item.item_price为下单单价，均不能等同于商品标价，因此无法计算平均标价。

**推理完全正确**——在它看到的 Schema 里，确实没有标价字段。

问题是这段中文被原样当成 SQL 送进了执行器：

```text
执行报错：只允许执行 SELECT / WITH 查询。
```

`clean_sql()` 会剥 Markdown、剥前缀、提取 SELECT/WITH 开头的片段，
但**没有"模型在拒答"这个分支**——提取不到 SQL 时，它把整段文本当 SQL 返回了。

正确行为应该是识别出这是拒答，把缺失原因原样透给用户，而不是伪装成一次执行失败。

---

## 亮点：陷阱题 5/5

五道 Schema 根本支撑不了的题（手机号、库存、员工数、物流时效、精确年龄），**全部诚实说明缺失，没有一道编答案**。

E50 是其中最阴的一道：库里有 `age_group` 年龄段，将就着拿来当"年龄"回答非常自然。模型没将就。

这个指标不专门测就永远不知道。而它恰恰是**最影响信任**的一项——
一个偶尔答错的系统还能用，一个会一本正经编数据的系统不能用。

## 按考点拆分：强弱非常集中

```text
排序取TopN     0/3  ░░░      全挂在"返回 ID 不返回名字"
比率计算       0/3  ░░░      两个聚合相除
区间对比       0/1  ░
层级类目       1/3  █░░      一级类目要多跳一次父子关系
多跳JOIN       1/3  █░░
─────────────────────────────
枚举值匹配      6/6  ██████
金额字段辨析     5/5  █████   9 个金额字段没被带偏
陷阱题         5/5  █████
纯口径词       3/3  ███      "客单价"全对
同名字段干扰     5/6  █████░  两表同名 city / pay_amount
```

前面花大力气做的元数据（近义字段辨析、业务别名）**确实起作用了**——
金额辨析 5/5、纯口径词 3/3、同名字段 5/6，这几类恰恰是最依赖元数据质量的。

弱的地方也很集中，不是均匀地差：TopN 输出、比率计算、多跳 JOIN。
**这就是分指标的价值——它把"76%"变成了一张可以照着干活的清单。**

## 经验

- **评测集的第一版，测出来的多半是评测本身的问题。**
  10 题那版跑了三轮：第一轮是网络超时，第二轮是我预设了唯一路径、
  第三轮是我的题目输出列有歧义。直到第四轮才抓到真 bug。
  出题人对"标准答案"的预设，和系统的真实表现同样需要被质疑。
- **满分不是好消息。** 它通常意味着题目太简单，而不是系统太强。
- **分指标比总分有用得多。** "76%"只能让人焦虑，
  "排序取 TopN 0/3、比率计算 0/3、检索漏掉名称字段"是一张可以照着干活的清单。
- **上一批的探针在这一批产生了价值。** `EMPTY_RESULT_SET` 接住了 E18 那个
  `WHERE 1=0`——如果没有它，这题只会显示"结果不符"，看不出是检索漏字段导致的。
  可观测性和评测是一对：前者定位，后者度量。

## 附录：一个虚假告警

跑本地 bge 向量召回时，每次都刷三行警告：

```
vector_index.py:50: RuntimeWarning: divide by zero encountered in matmul
vector_index.py:50: RuntimeWarning: overflow encountered in matmul
vector_index.py:50: RuntimeWarning: invalid value encountered in matmul
```

看着像数值算错了。实测下来不是：

```
索引矩阵: (81, 512) float32 contig= True
NaN/Inf: False False
捕获到的警告数: 3
scores NaN? False | top3 score: [0.5927 0.5711 0.5654]
```

矩阵没有 NaN/Inf，输出也没有 NaN，检索结果完全正确。
这是 numpy 2.x 搭配 macOS Accelerate BLAS 的已知现象：
矩阵乘法的 SIMD 内核会置位浮点异常标志，numpy 读到标志就报警，
但实际输出是干净的。

处理方式是在该处窄范围屏蔽，并写清楚为什么：

```python
with np.errstate(all="ignore"):
    scores = self.embeddings @ query_vector
```

**留一句注释很重要**——否则下一个人看到这行 `errstate`，
只会觉得是在掩盖数值问题。

## 小结

| # | 表面现象 | 真实根因 | 排查入口 |
|---|---|---|---|
| 一 | 模型说"Schema 里没这个字段" | 精排名额按小库调的 | 打印检索实际命中的字段 |
| 二 | CoT 正常但没有后续 | 正则依赖标点分隔符 | 检查 `cot_result.steps` 是否为空 |
| 三 | 12 个用例跑 36 秒 | `.env` 被测试进程读到 | 对比加 `.env` 前后的耗时 |
| 四 | 追问查出了全部 15 家店 | 关键词抽取拿的是原始 Query | 看抽出来的关键词里有没有代词 |
| 五 | SQL 返回 0 行 | 模型从店铺名里抠数字当 ID | 把 SQL 里的字面量和真实值对一遍 |
| 六 | 答"上下文没有客单价的定义" | data_qa 拿不到 business_meta | 检查该分支的 Prompt 里到底有什么 |

六个问题都不是"报错了去修"，而是**得先注意到有问题**。
写 LLM 应用最需要警惕的就是这类静默降级：
链路跑通、退出码 0、输出看着合理，但中间某一环已经悄悄失效了。

## 后续：给静默失败装上告警

三个问题都修完之后，剩下一个更根本的问题没解决：**下次再出同类问题，还是得靠肉眼发现。**

所以补了一层可观测性。做法很简单——把代码里每一处「出问题时会安静降级」的地方
找出来，装上探针。一共 6 处：

| Code | 触发条件 |
|---|---|
| `COT_PARSE_EMPTY` | 模型有输出，但一个四元组都没解析出来 |
| `SCHEMA_RECALL_CAPPED` | 精排名额 / 候选数 < 25%，且候选数 ≥ 10 |
| `MODEL_MOCK_FALLBACK` | 没 Key，CoT 或 SQL 走写死的 Mock |
| `RERANK_MOCK_FALLBACK` | 没 Rerank 服务，精排走规则排序 |
| `EMBEDDING_MOCK_FALLBACK` | 向量是哈希伪向量 |
| `COLUMN_SAMPLES_FAILED` | 字段样例值抽取抛异常被吞掉 |

告警走两条路：写 `logging`（默认落 stderr，保证不会完全无声），
同时进 `PipelineResult.diagnostics`（方便程序判断和写断言）。

### 关于阈值的一点取舍

`SCHEMA_RECALL_CAPPED` 的判据是**保留比例**而不是绝对数量：

```python
if (len(rerank_candidates) >= 10
        and rerank_top_n < len(rerank_candidates) * 0.25):
```

截断本身是正常的——精排的职责就是从候选里挑。真正异常的是「砍掉了绝大多数候选」。
用比例而不是绝对值，才能同时适配 9 个字段的小库和 81 个字段的大库，
不用为每个库单独配一个阈值。

`候选数 >= 10` 这个下限是为了避免小库误报：候选本来就只有 5 个、精排留 2 个，
比例是 40%，但这完全正常。

### 用它复现问题一

把精排参数调回出事前的值，告警立刻触发：

```
[SCHEMA_RECALL_CAPPED] 精排名额相对候选数过小，可能已截掉需要的字段，
建议调大 rerank_top_multiplier / rerank_min_top_n
（关键词数=2，候选数=20，精排名额=4，保留比例=20%）
```

换回当前参数，不再告警。这两个断言都写进了
`tests/test_diagnostics.py::RecallCapDiagnosticTestCase`。

### 顺带解决的一个问题

以前判断「我现在跑的到底是真模型还是 Mock」，只能盯着 CoT 输出看它是不是那段写死的文本。
现在 Demo 最后直接告诉你：

```text
9. 本次运行的降级记录
共 4 条。结果看着正常，但以下环节实际已经打了折扣：
  ⚠️  [MODEL_MOCK_FALLBACK] 未配置 API Key，CoT 规划降级为写死的 Mock 结果……
```

配好之后是：

```text
【6】降级记录
    无降级，链路每一环都在满配置下跑完
```

### 经验

- **降级不是错误，但降级必须留痕。**「优雅降级」和「静默失效」只隔一行日志。
- **告警的阈值要用比例，不要用绝对值**，否则换个规模的库就得重调。
- **把踩过的坑写成断言。** 排查记录会被忘记，测试不会。
  上面两条回归守卫，比这份文档本身更能防止同样的问题重来一次。
