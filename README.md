## 摘要

这份 README 是按时间顺序写的实验记录，很长。这一节只讲三件事：做了什么、测出了什么、
还剩什么。每条都链到正文，数字以正文为准。

### 做了什么

在基线链路上补了这些：

- **可靠性**：拒答前用全量 Schema 复核一次；筛选值守卫（拿库里的枚举取值检查 SQL 有没有
  丢筛选条件）；时间约束保底；SQL 报错的回调修正；9 个静默降级告警码
- **检索与生成**：本地 bge 向量与精排；按关键词分配精排名额；SQL 生成能看到样例值，
  并加了日期区间、整数除法、跨表比例三条 SQLite 规则
- **数据**：自建 11 表 81 字段的电商库（刻意埋了近义字段）；接入外部公开库 Chinook
  （64 字段，英文命名，中文提问）
- **评测**：按环节拆开的分指标、`--repeat` 压噪声、基础设施故障熔断；三套盲写留出集，
  都在第一次运行之前冻结提交
- **其他**：多轮追问的指代消解、把每一步中间产物摊开的 Web 界面、Schema 索引接进主链路

### 测出了什么

| 题库 | 是否照着它调过 | 端到端 | 首轮检索召回 |
|---|---|---|---|
| ecommerce 主题库　61 题 × 5 | 调过 | 60/61，唯一失败 E30 是判分问题，校正后 5/5 | 93/95 |
| Chinook 主题库　15 题 × 3 | 调过 | 15/15 | 18/18 |
| [留出集一](#留出集在没调过的题上测一次)　ecommerce 30 + Chinook 15 | 没有，已封存 | 29/30、15/15 | 74/74、26/31 |
| [留出集二](#第二套留出集修-chinook-精排在没见过的题上验证)　Chinook 20 | 没有，已用过 | 19/20 | 修精排前 88% → 修后 98% |
| [留出集三](#第三套留出集两个改动在没见过的题上)　ecommerce 30 + Chinook 20 | 没有，已用过 | 29/30、20/20 | 134/135 |

所有题库上的陷阱题诚实率都是 100%。留出集三这一行是"删精排文本"那个版本的成绩；之后的
"只留保底"和整数除法规则，是看了这套题的结果才做的，还没在陌生题上测过。

几条主要结论：

1. **拒答要建立在完整信息上。**模型常把"我没看到这个字段"说成"库里没有"。拒答前用全量
   Schema 复核一次之后，诚实率和准确率同时到了最好：端到端 82% → 90%，诚实率 80% → 100%。
   见[拒答必须建立在完整信息上](#拒答必须建立在完整信息上)
2. **元数据的收益先落在检索上。**Chinook 首轮召回 50% → 94%，ecommerce 端到端 +8 个点。
   能不能传导到准确率，取决于字段到齐之后题目还剩多少难度。见
   [真正的变量不是 Schema 大小，是题目难度](#真正的变量不是-schema-大小是题目难度)
3. **手写的精排文本比系统自动生成的还差。**全部删掉之后，Chinook 留出集首轮召回
   88% → 98%；ecommerce 留出集上 6 道题变好、0 道变差
4. **分数涨了，先问是系统变了还是判分变了。**主题库 87% → 98% 这 11 个点里，大约一半是
   判分校正，系统原本就答对了。见[这条线的账](#这条线的账)
5. **最危险的是零告警的错答案**：链路跑通、退出码 0、数字看着合理。降级告警和筛选值守卫
   都是为它做的。见[静默降级告警](#静默降级告警)、[筛选值守卫](#堵住零告警筛选值守卫)
6. **有两个机制做了，但没有收益。**自洽性投票净效果为零，成本 2.7 倍，默认关闭
   （[原因](#自洽性投票数学上有前提当前净效果为零)）。Schema 索引在当前规模下省不了时间，
   启动耗时的 98% 花在加载模型上（[原因](#先说清楚当前规模下没有性能收益)）

### 还剩什么

- **候选池的结构问题**：只被一个关键词命中的字段，在 RRF 里抢不过被几个关键词同时命中的
  字段。时间字段靠保底接住了，结构本身没改
- **最近三处改动需要第四套盲写题来验证**："只留保底"、[整数除法规则](#整数相除和跨表比例)、
  [筛选值守卫跳过题目自带口径的取值](#题目自带口径的取值守卫不再查)
- **测试范围**：只在 SQLite、最多 81 个字段的库上测过。全量复核的前提是整份 Schema 能放进
  提示词；换成放不下的大库，现在靠复核救回的那些题就会变成错答案
- **判分的局限**：每行的值先排序再比，所以把员工和上级的名字对调也会判对；单次运行有大约
  ±5% 的波动，结论都要靠 `--repeat` 来支撑

## 当前链路

```text
用户Query
  ↓
关键词抽取
  ↓
Schema混合检索 + RRF + Rerank
  ↓
SchemaGraph
  ↓
CoT四元组规划
  ↓
SQL生成
  ↓
MCP路由执行
  ↓
查询结果
```

动态路由会先结合长短期记忆判断用户意图：需要新业务数据时进入上述 Text2SQL 链路；结果解释、指标说明、历史结果追问和业务知识问答进入 `data_qa` 链路，不执行数据库查询。

路由实现位于 `askdata_pipeline/routing.py`，统一编排入口位于 `askdata_pipeline/dynamic_service.py`，对话问答实现位于 `askdata_pipeline/data_qa.py`。

结果校验与回调修正是后来补上的，见[结果校验与回调修正](#结果校验与回调修正--自洽性投票)。

### 关于 thinking 模式

DeepSeek 默认开启思考模式，而**思考模式下 `temperature` 参数会被忽略**。
项目按场景分别处理：

- CoT 四元组规划：显式开启思考（`thinking.type = enabled`），这本来就是推理场景
- SQL 生成、关键词抽取：显式关闭思考，让 `temperature=0.0` 真正生效，保证输出确定性

## 电商数据集

原始的 `trade` 数据集只有 2 张表 9 个字段，随便召回几个字段就全命中了，
两阶段检索这套机制其实没派上用场。`ecommerce` 数据集用来补这一课。

### 规模

| 分层 | 表 | 说明 |
|---|---|---|
| dim | `dim_user` `dim_shop` `dim_product` `dim_category` | 用户、店铺、商品、类目 |
| fact | `fact_order` `fact_order_item` `fact_payment` `fact_refund` `fact_user_behavior` | 订单、明细、支付、退款、行为 |
| dws | `dws_user_summary` `dws_shop_daily` | 用户累计指标、店铺日报 |

合计 11 张表、81 个字段、约 7000 行数据，固定随机种子生成，每次结果一致。
dws 汇总层由事实表聚合而来，`SUM(dws_shop_daily.gmv)` 与 `SUM(fact_order.order_amount)` 严格相等。

### 刻意埋的坑

这套 Schema 专门设计了几组近义字段，用来检验检索的区分能力：

- **9 个金额字段**：`order_amount`（订单原价）、`pay_amount`（实付）、`discount_amount`（优惠）、
  `freight_amount`（运费）、`refund_amount`（退款）、`item_amount`（明细）、
  `gmv`（成交总额）、`total_pay_amount`（累计实付）、`avg_order_amount`（客单价）
- **`pay_amount` 在两张表里都有**：`fact_order` 里是订单实付，`fact_payment` 里是支付流水
- **`city` 在两张表里都有**：`dim_user.city` 是买家所在地，`dim_shop.city` 是店铺经营地
- **`finish_time` 在两张表里都有**：订单里是确认收货，退款里是退款到账
- **纯业务口径词**：用户说“客单价”“销售额”，字段名叫 `avg_order_amount`、`gmv`，字面零重合

### 检索参数要随 Schema 规模放大

`rerank_top_n = 关键词数 × rerank_top_multiplier`。默认的 multiplier=2 对 9 个字段的
trade 库够用，但在 81 个字段上，2 个关键词只保留 4 个字段，必然漏召回。
`text2sql_pipeline._build_retrieval_config()` 里只有 trade 显式用小参数，
其余一律默认走大库参数：multiplier=6、min_top_n=10、max_top_n=30、RRF final_top_k=60。

**这是把 Demo 搬到真实库时最容易踩的坑**——链路没报错，只是悄悄少给了几个字段，
表现为模型说“Schema 里没有这个字段”。

这个坑后来又踩了一次。原先的写法是反过来的：只有 ecommerce 显式放大，其余落进
小库参数。Chinook（64 个字段）接入时没人记得加分支，悄悄用了 9 个字段的参数，
2 个关键词只留 4 个精排名额（见[第二套留出集](#第二套留出集修-chinook-精排在没见过的题上验证)）。
**默认值应该是安全的那一个**——新接入的库，宁可候选多一点，也别悄悄漏字段。

### 换成你自己的库

照着 [ecommerce_data.py](askdata_pipeline/ecommerce_data.py) 改三处：

1. `sql/create_*.sql` 换成你的建表语句，**外键一定要声明**，表关系是靠它自动提取的
2. `get_*_business_meta()` 写字段的业务含义和别名——这份元数据的质量直接决定召回准确率
3. `_prepare_dataset()` 里加一个分支

元数据里最值钱的是 `aliases` 和近义字段的辨析：把业务口头怎么说、这个字段和那个字段差在哪
写清楚，检索准确率的提升比换更大的模型明显得多。

这句话在一个**不是我设计的库**上做过消融验证——首轮检索召回率 50% → 94%，
见 [Chinook 元数据消融](#元数据消融把元数据整份拔掉)。

## 静默降级告警

这个项目最难发现的不是报错，是「链路跑通、退出码 0、输出看着合理，
但中间某一环已经悄悄失效了」。三个真实案例见 [docs/排查记录.md](docs/排查记录.md)。

[askdata_diagnostics.py](askdata_diagnostics.py) 给每一处已知的降级点装了探针：
出问题时要么在 stderr 留下一行告警，要么被 `PipelineResult.diagnostics` 带出来。

### 降级码

| Code | 含义 | 后果 |
|---|---|---|
| `COT_PARSE_EMPTY` | CoT 有输出但没解析出四元组 | **一条 SQL 都不会生成**，链路安静停住 |
| `SCHEMA_RECALL_CAPPED` | 精排名额相对候选数过小 | 可能已截掉需要的字段，模型会说「Schema 里没这个字段」 |
| `MODEL_MOCK_FALLBACK` | 没 Key，CoT / SQL 走写死的 Mock | 换任何非内置 Query 都会返回缺失或 `SELECT 1` |
| `RERANK_MOCK_FALLBACK` | 没 Rerank 服务，精排走规则排序 | 只覆盖内置词表，没有通用语义判断 |
| `EMBEDDING_MOCK_FALLBACK` | 向量是哈希伪向量 | 语义召回实际失效，只剩字面匹配 |
| `COLUMN_SAMPLES_FAILED` | 字段样例值抽取失败 | 索引文本少一块语义，召回质量下降 |
| `FILTER_VALUE_DROPPED` | 问题提到的枚举取值没出现在 SQL 里 | 筛选条件疑似被丢，已带提示重规划；见[筛选值守卫](#堵住零告警筛选值守卫) |
| `FILTER_GUARD_DISABLED` | 筛选值守卫建索引失败 | 检索漏掉筛选字段时回到零告警 |
| `TIME_FIELD_RESCUED` | 问题有时间约束，检索结果里却没有最贴题的时间字段 | 已从数据覆盖该时段的时间字段里补回；见[时间字段](#时间字段让精排看得见年份再给时间约束保底) |

### 怎么看

Demo 会在最后集中展示：

```text

```

```text
【6】降级记录
    无降级，链路每一环都在满配置下跑完
```

代码里读：

```python
result = pipeline.run(query)

if result.diagnostics:
    for item in result.diagnostics:
        print(item.render())
```

自己的代码里收集：

```python
from askdata_diagnostics import collect

with collect() as diagnostics:
    ...  # 跑链路
```

`collect()` 基于 `contextvars`，只覆盖当前执行上下文。
后台线程（例如记忆模块的异步摘要）里的降级仍然会写 logging，但不进 `collect()` 列表。

## 多轮追问

单轮问答只考验 Text2SQL，多轮真正难的是**指代消解**：
用户第二句说「它们的退款金额呢」，「它们」指的是上一轮 SQL 查出来的那三家店铺——
这个信息不在当前 Query 里，只存在于会话记忆中。

```bash
python -m askdata_pipeline.multi_turn_demo
```

五轮对话覆盖四种典型形态：

| 轮次 | 问题 | 路由 | 查库 | 考点 |
|---|---|---|---|---|
| 1 | 销售额最高的三个店铺是哪些 | `database_query` | 是 | 基线，纯 Text2SQL |
| 2 | 它们的退款金额分别是多少 | `database_query` | 是 | 指代消解 + 新数据需求 |
| 3 | 刚才第一名的店铺叫什么名字 | `data_qa` | 否 | 复用历史结果，不打数据库 |
| 4 | 客单价这个指标是怎么算的 | `data_qa` | 否 | 指标口径问答 |
| 5 | 帮我查一下这些店铺的买家数 | `database_query` | 是 | 指代对象已滑出短期窗口 |

### 指代消解是独立的一步

把会话记忆拼在 Query 前面一起送进 CoT，指望模型顺手解决——实测不行，两种失败都会出现：

- **关键词抽取拿到的是原始 Query**，把「它们」当成了检索词，真正的指代对象根本没进检索
- **CoT 看到了上下文但没被要求先解指代**，结果要么忽略限定条件查了全表，
  要么从店铺名「臻品自营店15」里抠出数字 15 当成 `shop_id`，凭空造出一个过滤条件

所以 [query_rewriter.py](askdata_pipeline/query_rewriter.py) 把它拆成显式的一步，
放在关键词抽取**之前**：

```text
用户：它们的退款金额分别是多少
  ↓ 指代消解
销售额最高的三个店铺"臻品自营店15""优选旗舰店1""旗舰旗舰店7"的退款金额分别是多少
  ↓ 关键词抽取
销售额，店铺，臻品自营店15，优选旗舰店1，旗舰旗舰店7，退款金额
  ↓ SQL
WHERE dim_shop.shop_name IN ('臻品自营店15', '优选旗舰店1', '旗舰旗舰店7')
```

改写 Prompt 里有一条专门约束：**绝对不要凭空推断任何 ID**。
店铺名叫「臻品自营店15」不代表它的 ID 是 15——这是实测中模型真实犯过的错。

只有检测到指代词（它们、这些、刚才、上述……）才会调模型，自包含的问题直接短路，
不浪费一次调用。

### 指标口径问答要看得见 Schema

`data_qa` 原本只拿得到会话记忆，问「客单价怎么算的」只能回答「上下文里没有定义」。
但 `dws_user_summary.avg_order_amount` 的元数据里明明写着「业务上叫客单价」。

`build_metric_glossary()` 把 `business_meta` 压成一份指标口径表喂给 `data_qa`，
现在能直接定位到表名、字段名和业务含义。

### 相关降级码

| Code | 触发条件 |
|---|---|
| `QUERY_REWRITE_SKIPPED` | 检测到指代词但没 Key，多轮追问结果大概率不正确 |
| `QUERY_REWRITE_FAILED` | 指代消解调用失败，已回退为原始 Query |
| `EMPTY_RESULT_SET` | SQL 执行成功但返回 0 行，筛选条件可能有问题 |

`EMPTY_RESULT_SET` 就是为幻觉 ID 这类问题准备的——
`WHERE shop_id IN (15, 1, 7)` 不会报错，只会安静地返回 0 行。

### 为什么需要它

在有评测集之前，每次改动都是「跑一条 Query 看对不对」。这带来两个问题：

- **没法回答"提升了多少"。**元数据写得再细，也只能说「感觉准了」。
- **bug 是撞见的，不是测出来的。**曾经有一个 SQL 表名前缀的 bug，
  同一道题连过两轮、第三轮才挂——手跑单条 Query 有 2/3 的概率看不见它。

### 三个指标分开统计

| 指标 | 衡量什么 | 定位到 |
|---|---|---|
| 首轮检索召回率 | 检索这一轮就召回了，没靠兜底 | 检索环节 |
| Schema 召回率 | 最终进 Prompt 的 Schema 里有没有 | 检索环节 + 兜底 |
| 执行准确率 | 结果集与参考答案是否一致 | 生成环节 |
| 陷阱题诚实率 | Schema 支撑不了时会不会编 | 可靠性 |
| 端到端准确率 | 整条链路 | 总分 |

前两个的差就是[全量 Schema 复核](#拒答必须建立在完整信息上)兜掉的量。
只看第二个会漏掉检索的真实水平——这个坑的完整经过见
[元数据消融](#先得修尺子原来的召回率测不出这个差别)。

召回 92% 但端到端 61%，说明问题在 CoT 或 SQL 生成；两个都低，说明元数据没写好。
**一个总分只能告诉你「不行」，分指标才能告诉你「哪不行」。**

### 判分方式

**不比 SQL 字符串，比执行结果。**同一个问题有无数种正确写法
（JOIN 条件左右互换、列别名不同、子查询 vs JOIN），比字符串没有意义。
比对时只看**值**不看列名，行内值排序、行间集合比对，
这样容忍列别名和排序差异，但抓得住值错、行数错、筛选条件错。

两条从踩坑里学到的规矩：

- **`must_hit_columns` 支持候选组。**同一个问题常有多条正确路径——
  「某天的订单量」既能数 `fact_order.create_time`，也能用
  `dws_shop_daily.stat_date`。只认一条路径，测的就不是系统而是出题人的预设。
- **题目措辞必须让输出列无歧义。**问「客单价最高的10个用户的客单价是多少」，
  模型多返回一列 `user_id` 不能算错。输出不明确的题目没法客观判分。

### 单次运行有误差，用 --repeat 压掉

同一份代码、同一份题目跑两次，50 题里有 **5 题结果不一样**：

```text
E18  第一次 ✅ → 第二次 ❌        E28  第一次 ❌ → 第二次 ✅
E24  第一次 ✅ → 第二次 ❌        E39  第一次 ❌ → 第二次 ✅
E38  第一次 ✅ → 第二次 ❌
```

源头是关键词抽取本身非确定：模型这次吐「直播间」、下次吐「渠道」，
一路级联到召回、精排和最终 SQL。单次运行因此带着约 ±5% 的误差棒。

**这意味着单次跑出来的前后对比基本是在噪声里找信号。**

```bash
python -m eval.runner --repeat 3
```

重复模式下：

- 每题按**多数**判定通过，展示 `2/3`、`0/3` 这样的通过次数
- 输出单次运行分布和波动幅度：`40/50　38/50　41/50　→　76% ~ 82%，波动 3 题`
- 单列**抖动题**（同一份代码结果不一致的那些）

抖动题本身就是脆弱信号：它说明这道题的链路某一环依赖了模型的随机输出，
比稳定失败的题更值得先看——稳定失败是能力问题，抖动是鲁棒性问题。

### 熔断：宁可没有数字，也不要假数字

一次 150 运行的评测跑到一半断网，后面 26 题全部 0.0 秒失败，重试机制空转 162 次，
最后仍然吐出一份**格式完整的报告**：

```text
端到端准确率     21/50    42%
陷阱题诚实率      0/5      0%
单次运行分布　21/50　21/50　21/50　→　42% ~ 42%，波动 0 题
```

每个数字都是假的。那句"波动 0 题"看着像好消息，其实是故障的指纹——
真正的随机抖动不可能三次完全一致。

如果不逐题去看耗时，很容易把 42% 当成真实退步，然后去修一个根本不存在的问题。
**一个会输出无效数字的评测器，比没有评测器更危险。**

现在评测器会：

1. **区分故障类型。**DNS 失败、Key 失效、余额耗尽属于持续性故障，**不重试**——
   重试一百次也是一样的结果，只会白烧时间掩盖问题。超时、限流才值得重试。
2. **连续 3 次基础设施故障就中止**（`--abort-after` 可调），退出码 2。
3. **中止时一个百分比都不输出。**半截数据算出来的准确率没有意义，
   而一旦印成百分数就会被当成结论。

```text
⛔ 评测未完成，不输出指标
  中止原因　连续 3 次基础设施故障
  故障类型　persistent
  完成进度　23/50 题

  半截数据算出来的准确率没有意义，因此这里不给任何百分比。
  请先排查环境（网络 / DNS / API Key / 余额 / 限流），再重跑。
```

注意 SQL 报错、结果不符这类**系统真实失败**不计入熔断计数，只有环境故障才算。

## 拒答必须建立在完整信息上

陷阱题诚实率这个指标，一度经历了"假 100% → 真 60% → 78% 但误伤 → 100% 且准确率同涨"的曲折。
过程比结论更值得记：

**第一步，发现尺子是坏的。**判分逻辑原本是"CoT 文本出现『缺失』二字就算通过"。
收紧成"给出数字即判编造"之后，真实成绩是 3/15——系统一直在编，
只是判分接受了"嘴上承认、手上照编"。最离谱的一例：

```sql
-- 问"每家店铺有多少名员工"，库里根本没有员工数据
SELECT shop_name, COUNT(*) AS employee_count FROM dim_shop GROUP BY shop_name
-- 每家店恒为 1，标上 employee_count 就交了
```

**第二步，修过头了。**在 CoT Prompt 里写下"宁可回答缺失，也不要给出口径不符的数字"，
再加上结构化阻断（CoT 判缺失就不生成 SQL）。陷阱题 15/15，但**误伤了 5 道正常题**，
端到端从 82% 掉到 78%。

原因在 CoT 的实际输出里：

```text
Q: 北京用户一共下了多少笔订单
数据库: 缺失
处理对象: 缺少 dim_user 的城市字段（如 city/province）用于筛选"北京"用户
```

`dim_user.city` **明明存在**，只是这一轮没被检索召回。
那句"宁可回答缺失"让模型把**"我没看到"**和**"库里没有"**混为一谈。

**第三步，找到真正的变量。**问题从来不在诚实和准确之间取舍，
而在于**做判断时有没有完整信息**。所以：拒答之前，用全量 Schema 复核一次。

```python
if any(_is_missing_schema_step(step) for step in cot_result.steps):
    full_graph = self._build_full_schema_graph()   # 全部 81 个字段
    retry = self.cot_planner.plan(contextual_query, full_graph)

    if not any(_is_missing_schema_step(s) for s in retry.steps):
        emit(Codes.SCHEMA_RECALL_MISS, "实为检索漏召回，已用全量 Schema 重规划")
        cot_result = retry
```

81 个字段放进 Prompt 完全放得下，只在判缺失时多花一次调用。
**一个拒答如果建立在残缺信息上，就没有任何可信度。**

### 结果：两个指标同时到最好

| 指标 | 基线 | 只加诚实约束 | 加全量复核 |
|---|---|---|---|
| Schema 召回率 | 94% | 93% | **99%** |
| 执行准确率 | 82% | 87% | **91%** |
| 陷阱题诚实率 | 80% | 100% | **100%** |
| 端到端 | 82% | 78% | **90%** |

这张表里的 Schema 召回率是**复核后**口径，兜底兜掉多少当时测不出来——
补测见[99% 里有 6 个点是兜底撑的](#回头补测-ecommerce99-里有-6-个点是兜底撑的)。

端到端 82% → 90%，跳出了基线 78~84% 的误差带。
顺带修好了两道**原本稳定失败**的题（E07、E30）——
它们的根因也不是能力不足，是信息不够。

### 把 bug 变成了探针

两个降级码讲出了完整的故事：

```text
SCHEMA_INSUFFICIENT    18 题次    复核后确认缺失，正确阻断
SCHEMA_RECALL_MISS     13 题次    复核后发现能答，检索确实漏了
```

`SCHEMA_RECALL_MISS` 那 13 次是以前根本测不出来的数据。
模型的"缺失"声明成了一个精确的召回失败探针——比任何启发式都准，
因为它是模型自己在说"我需要城市字段但没看到"。

## Chinook：换一个不是我设计的库

前面所有数字都建立在一个闭环上——数据集是我造的，50 道题是我出的，元数据也是我写的。
「元数据质量决定召回准确率」这个结论，在自己搭的场子里当然成立。

[Chinook](https://github.com/lerocha/chinook-database) 是公开的音乐商店示例库，
11 张表 64 个字段，英文命名。它自带的歧义比我刻意埋的还狠：

| 歧义 | 情况 |
|---|---|
| `Name` | 出现在 **5 张表**：`Artist` `Genre` `MediaType` `Playlist` `Track` |
| Customer / Employee | 共享 **11 个同名字段**：`City` `Country` `Email` `Phone` `FirstName`… |
| `Title` | `Album.Title` 是专辑名，`Employee.Title` 是职位 |
| `UnitPrice` | `Track` 里是目录标价，`InvoiceLine` 里是成交快照 |

**这些歧义不是我埋的**——这正是它作为验证集的价值。题库 15 题
（[cases_chinook.py](eval/cases_chinook.py)），中文提问、英文 Schema，含 2 道陷阱题，
难度组合就是真实场景：国内团队用英文命名的库，业务同学用中文提问。

```bash
curl -L -o runtime_data/chinook.db \
  https://github.com/lerocha/chinook-database/raw/master/ChinookDatabase/DataSources/Chinook_Sqlite.sqlite

python -m eval.runner --dataset chinook --repeat 3
```

### 元数据消融：把元数据整份拔掉

Chinook 还能测第二件事，而且能测干净：同一个库、同一套题、同一份代码，
**唯一的变量是业务元数据的有无**。

```bash
python -m eval.runner --dataset chinook --meta ab --repeat 3
```

`--meta none` 把手写的表描述、字段别名、近义字段辨析全部丢掉，只留库里自带的
字段名、类型和样例值；`--meta ab` 两组都跑并输出差值。两组**逐题交错跑**，
不是一组跑完再跑另一组——否则接口在中途变慢或变笨，差值里就混进了时间因素。

写元数据时守的纪律是**只描述 Schema，不看题库**：
每句话都必须是"一个刚接手这个库的数据同学照着表结构和样例值就该写下来的话"。
歧义辨析来自上面那张表，不来自题目——否则元数据就成了答案抄写，差值也就没有意义。

15 题 × 3 次 × 2 组 = 90 次运行：

| 指标 | 无元数据 | 有元数据 | 变化 |
|---|---|---|---|
| **首轮检索召回率** | 9/18　50% | 17/18　94% | **+44pt** |
| **复核救回次数** | 21/45 次 | 3/45 次 | **−18 次** |
| **平均每次耗时** | 8.5s | 6.6s | **−22%** |
| Schema 召回率（含兜底） | 18/18　100% | 18/18　100% | 持平 |
| 执行准确率 | 13/13　100% | 13/13　100% | 持平 |
| 陷阱题诚实率 | 2/2　100% | 2/2　100% | 持平 |
| 端到端准确率 | 15/15　100% | 15/15　100% | 持平 |

差别集中在 6 道题上。无元数据时它们**每次**都要靠全量 Schema 复核救回，
有元数据后一次都不用救：

```text
C02  所有发票的金额合计        首轮漏召回 Invoice.Total
C06  每个流派各有多少曲目      首轮漏召回 Genre.Name、Track.GenreId
C08  Rock 流派总时长          首轮漏召回 Genre.Name
C09  开票金额最高的三个国家    首轮漏召回 Invoice.Total
C11  消费总额最高的客户        首轮漏召回 Customer.FirstName、Invoice.Total
C12  平均每张发票几个明细行    首轮漏召回 InvoiceLine.InvoiceId
```

### 端到端持平，不等于元数据没用

**天花板在加元数据之前就顶住了**，顶住它的是[全量 Schema 复核](#拒答必须建立在完整信息上)。
Chinook 只有 64 个字段，全量 Schema 塞得进 Prompt，所以每一次漏召回都能被捞回来——
无元数据组 45 次运行里有 **21 次（47%）** 是这么救回来的。

代价记在耗时上：两组总耗时差 86.3s，正好省掉 18 次复核，摊下来 **4.8s 一次**，
就是一轮 CoT 规划的往返时间。这个提速和机制对得上，不是接口抖动。

所以这份 A/B 能说的是：**元数据把检索从「一半靠兜底」变成「一次到位」**。
至于它能不能救准确率，这套 15 题验证不了——后来在 ecommerce 上补了一组，
答案是能、值 8 个点，但机制和我当时猜的不一样：
见[真正的变量不是 Schema 大小，是题目难度](#真正的变量不是-schema-大小是题目难度)。

### 先得修尺子：原来的召回率测不出这个差别

第一次跑完 A/B，四个指标**全部持平 100%**，结论看起来是"元数据毫无作用"。

问题出在 `Schema 召回率` 算的是 `schema_context`——那是**复核之后**的 Schema。
一旦触发复核，它就被换成了全库 64 个字段，拿它算召回率等于在问
"全量 Schema 里有没有这个字段"，答案恒为 100%。

真相当时只藏在降级记录里：`SCHEMA_RECALL_MISS` 一组 21 题次、另一组 3 题次。

修法是给 `PipelineResult` 加一份 `retrieval_context`，存**首轮检索**的结果，
在复核改写 `schema_graph` 之前就留好；评测器据此新增两个指标：

| 指标 | 衡量什么 |
|---|---|
| 首轮检索召回率 | 检索这一轮就召回了，没靠兜底 |
| 复核救回次数 | 首轮漏召回、靠全量 Schema 重规划补上的运行数 |

**一个测不出变化的指标，和一个输出假数字的评测器是同一种病。**

新指标加完，第一件事是回头把 ecommerce 那 50 题重测一遍——那里记着的
"Schema 召回率 99%"是同一个复核后口径。

### 回头补测 ecommerce：99% 里有 6 个点是兜底撑的

50 题 × 3 次 = 150 次运行，跑的是当前出厂配置：

| 指标 | 重测 | [上面那张表](#结果两个指标同时到最好)记的 |
|---|---|---|
| **首轮检索召回率** | **62/67　93%** | 当时测不出来 |
| Schema 召回率（含兜底） | 66/67　99% | 99% |
| **复核救回** | **13/150 次运行　8.7%** | — |
| 执行准确率 | 41/45　91% | 91% |
| 陷阱题诚实率 | 5/5　100% | 100% |
| 端到端准确率 | 46/50　92% | 90% |

三项分毫不差，端到端 92% 落在原记的 86%~94% 误差带内——**那张表没问题，只是少了一行**。
真实的首轮召回是 93%，兜底兜掉 6 个点：67 个必中字段里的 4 个、150 次运行里的 13 次。

> 本节与下一节的数字是 **50 题口径**，且测于[强命中补回收紧](#追查-e24同义近邻让压倒性命中判据失效)**之前**。
> 题库后来扩到 61 题，当前基线见[先补秤](#先补秤题库扩到-61-题)：端到端 87%、
> Schema 召回率 97%。这里保留旧口径是因为元数据 A/B 的两组都在这个口径下跑的，
> 换口径重算会让差值失去出处。

漏召回的两处都在近义字段密集的地方：E19 漏 `fact_user_behavior.behavior_type`，
E27 漏 `fact_refund.refund_amount`。

### 在 ecommerce 上再做一次：元数据值 8 个点

Chinook 那组的结论停在"元数据买到的是检索，不是准确率"。但那是 64 个字段、
15 道相对直白的题。换到 81 个字段、50 道含嵌套聚合和比率的题上，同一个开关再拉一次
（50 题 × 3 次 × 2 组 = 300 次运行）：

| 指标 | 无元数据 | 有元数据 | 变化 |
|---|---|---|---|
| **首轮检索召回率** | 55/67　82% | 62/67　93% | **+10pt** |
| Schema 召回率（含兜底） | 63/67　94% | 66/67　99% | +4pt |
| 执行准确率 | 36/45　80% | 40/45　89% | **+9pt** |
| **端到端准确率** | **41/50　82%** | **45/50　90%** | **+8pt** |
| 陷阱题诚实率 | 5/5　100% | 5/5　100% | 持平 |
| 复核救回 | 25/150 次 | 15/150 次 | −10 次 |

两组的单次分布分别是 80%~82% 和 88%~90%，各自波动 1 题——**8 个点远在误差带之外**。

无元数据时漏召回的字段，全部落在[刻意埋的纯业务口径词](#刻意埋的坑)上：
`avg_order_amount`（客单价）、`freight_amount`（运费）、`discount_amount`（优惠）、
`item_amount`（成交金额）、`gmv`（销售额）、`stay_seconds`（停留时长）——
业务怎么说、字段怎么写，字面零重合。这正是当初设计这套 Schema 想考的东西。

**但不是单向变好**：翻正 7 题（E05 E07 E33 E38 E39 E42 E43），翻负 3 题（E23 E36 E37），
首轮召回另有 4 题变差——其中 E24「北京用户一共下了多少笔订单」，就是上面那个
经典漏召回案例，加了元数据反而从 1/1 掉到 0/1。净值是正的，
但**元数据不是无条件的改进**。

### 真正的变量不是 Schema 大小，是题目难度

|  | 无元数据 | 有元数据 |
|---|---|---|
| **ecommerce**　81 字段 · 50 题 | 首轮 82%　端到端 **82%** | 首轮 93%　端到端 **90%** |
| **Chinook**　64 字段 · 15 题 | 首轮 50%　端到端 **100%** | 首轮 94%　端到端 **100%** |

上面写过一个推论：*换一个字段多到塞不进 Prompt 的库，兜底不成立，
召回差距就会变成准确率差距*。**这个机制说错了**——81 个字段照样塞得进 Prompt，
兜底照样在跑（25 次），端到端还是掉了 8 个点。

真正的变量是题目难度。Chinook 无元数据的首轮召回只有 50%，比 ecommerce 无元数据的
82% 还差得多，端到端却稳在 100%：那 15 道题只要字段到齐就能答对，兜底把字段补齐就够了。
ecommerce 有嵌套聚合、比率、区间对比，**兜底能补上字段，补不了生成**——
E23、E36 两题元数据反而把首轮召回从 2/3 提到 3/3，端到端却翻负了。

所以完整的说法是：**元数据的收益先落在检索上（+10pt ~ +44pt），
能不能传导到准确率，取决于题目在字段到齐之后还剩多少难度。**

### 这个结论的边界

- **15 题、两组都 100%**，说明这套题对当前链路偏容易，测不出生成环节的任何差别。
- **C10「2023年一共开了多少张发票」两组都漏**：`Invoice.InvoiceDate` 首轮都没召回，
  每次都靠复核救回。给它写了别名和 `keyword_text` 也没用，这是元数据没吃下的一块。
- 有元数据组多出 6 次 `DOMINANT_KEYWORD_RESCUED`（字面命中压倒性的字段被精排淘汰又强制补回），
  说明精排阈值对高质量元数据偏保守了。**这条线索后来查下去了，见下一节。**

### 追查 E24：同义近邻让"压倒性命中"判据失效

上面那组 A/B 里有一处反常：**E24「北京用户一共下了多少笔订单」加了元数据反而漏召回**，
首轮从 1/1 掉到 0/1。它正是[全量复核那一节](#拒答必须建立在完整信息上)的原始案例，
值得查到底。

逐层拆开之后，元数据其实是有效的——**问题出在下游**。

**BM25 层：元数据把同名字段分开了**

```text
无元数据  『北京用户』:  user_name 22.12 │ dim_shop.city 10.55 │ dim_user.city 10.55 │ province 9.33
有元数据  『北京用户』:  dim_user.city 17.52 │ province 16.08 │ dim_shop.city 10.11 │ user_name 8.70
```

注意无元数据那行：`dim_shop.city` 与 `dim_user.city` **同为 10.55 分**——
两个字段的索引文本几乎等价，BM25 根本分不开。加元数据后 `dim_user.city` 升到第一，
消歧成功了。

**精排层：全部名额押给了 dws 汇总层**

另一个关键词『订单笔数』在有元数据时强命中 `dws_user_summary.total_order_count`
（"用户累计下单笔数"）。精排是**逐字段**打分的，它不知道"这组字段合起来能不能回答问题"，
于是 12 个名额全给了 dws 汇总层——而那张表没有城市维度，答不了"北京"这个筛选条件。
`dim_user` **整张表**被挤出了 SchemaGraph。

对比两组的精排分数，能看出元数据干了什么：

```text
无元数据  0.0015 / 0.0008 / 0.0007 …   ← 索引文本稀疏，精排无法区分，近似透传 RRF 顺序
有元数据  0.8002 / 0.7558 / 0.7140 …   ← 排序"确信"，于是确信地押错了
```

`dim_user.city` 在无元数据组活到第 5 位是**运气**，不是判断。

**强命中补回为什么没接住**

那个机制的判据是"甩开第二名 3 倍"。但 `dim_user.city` 17.52 vs `dim_user.province` 16.08，
比值 1.09——**第二名往往是第一名的同义近邻**，索引文本高度重合，分数天然咬得死紧，
谁也甩不开谁。无元数据时更极端：`dim_user.city` 与 `dim_shop.city` 同分，比值正好 1.00。

所以补了两条判据：分数达到 `min_score` 的 2 倍算强命中，不要求断层；
并列的近邻（0.85 倍以内）一起补回，分不清"北京"指 city 还是 province 就两个都给。

### 收紧：一个机制该不该留，看它的代价

第一版放开了写，**首轮召回上去了，稳定性掉下来了**：

| 指标 | 改前基线 | 放开版 | **收紧版** |
|---|---|---|---|
| 首轮检索召回率 | 93%　62/67 | **99%　66/67** | 94%　63/67 |
| 复核救回 | 13/150 | **3/150** | 11/150 |
| 补回触发 | 3 题次 | 34 题次 | 11 题次 |
| 执行准确率 | 91% | 87% | 89% |
| 端到端准确率 | 92% | 88% | 90% |
| 抖动题 | 7 道 | 12 道 | 9 道 |
| **单次分布波动** | **1 题** | **7 题** | **1 题** |

放开版触发了 34 次，等于每 4~5 次运行就往 SchemaGraph 里硬塞最多 4 个字段。
端到端 88% 单看还在误差带里，但**误差带本身变宽了**——三次分别是 47/50、40/50、45/50。
按[抖动是脆弱信号](#单次运行有误差用---repeat-压掉)那套判据，这是回归，不是改进。

收紧的办法是给强命中判据加一个前提：**该字段所属的表整张都不在命中集里**。
E24 的真实病灶是 `dim_user` 整张表消失、连 JOIN 都做不了；
而那 34 次里有三分之二是往已经在图里的表上再塞字段，纯噪声。

收紧后稳定性完全回到基线（波动 1 题、端到端 90%），触发降到 11 次。

**但收益也跟着缩了**：首轮召回只剩 94%，比基线高 **1 个字段**（62/67 → 63/67）。
Chinook 侧三版没有任何差别，都是首轮 94%、端到端 15/15。

所以如实记下来：**这个机制修的是一个已定位的真实缺陷，但在现有两套题上，
净收益约等于 1 个字段，代价为零。** 留着它是因为缺陷本身成立——换一个同名字段
更密集的库，同义近邻互相压制会比这里更常见——而不是因为它在这两套题上测出了什么。

> 这条"强命中 + 整表缺失"判据**后来被删了**，换成了
> [关键词覆盖约束](#关键词覆盖约束秤补对之后第一个测出真实收益的改动)——
> 覆盖判据把它要救的情形整个包住，而且解释更干净：E24 的病灶不是"表缺了"，
> 是**筛选意图整个丢了**。代码里已经没有 `dominant_keyword_strong_ratio` 这个旋钮。
> 这一节保留，因为"净收益 1 个字段"这个结论本身是下一步的起点。

### 先补秤：题库扩到 61 题

上一节的结论是"净收益约等于 1 个字段"。但这个数字有个问题——**它可能是秤的问题，
不是机制的问题**。当时 50 题的检索 headroom 只剩 4 个字段（首轮召回 94%，67 个必中
字段漏 4 个），E24 几乎是唯一的整表缺失案例。在这种余量下改检索，
**改进和退步长得一样**。

所以先补秤。新增 E51~E61 共 11 题，每道题都把**筛选条件和指标拆到不同的表上**——
这正是 E24 暴露的那类结构：精排逐字段打分，没有"这组字段合起来能不能回答问题"
的概念，于是把名额押给语义最近的那张表，而那张表缺的正是筛选维度。

| 题 | 考点 |
|---|---|
| E51 | 上海店铺 × 北京用户的已完成订单金额——两个 `city` 同时考 |
| E52 | 直播间 × 金卡会员的退款金额——三张表各出一个字段 |
| E53 | 美妆护肤类目的加购次数——层级类目 + 行为表 |
| E54 | 质量问题退款按店铺城市分布——筛选在事实表、维度在维表 |
| E55 | 上海店铺下旬减上旬的销售额差值——区间对比 + 跨表筛选 |
| E56 | 浏览过但没下单的用户数——两张事实表反连接 |
| E57 | 已完成订单里高等级会员的金额占比——条件聚合 + 比率 + 跨表 |
| E58 | 微信支付且退款的订单数——`pay_channel` 与 `fact_order.channel` 是两个渠道 |
| E59 | 两个不相连时间窗口的直播间订单数 |
| E60 | 在售与已下架商品的平均标价差 |
| E61 | 2024年注册用户的订单数——时间筛选在维表、指标在事实表 |

出题时按踩过的坑逐条校验：61 题参考 SQL 全部跑得通、`must_hit_columns` 里没有
不存在的字段名、没有 0 行或恒为 0 的退化答案。E55 的两条路径（dws 汇总层 /
fact 明细层）实测差值一致，所以两条都认。

**E51 第一版我自己踩了[判分方式](#判分方式)那条规矩**：原题没限定"已完成"，
模型加了 `pay_time IS NOT NULL`（只算真付过款的）得 75502.68，参考答案 76944.06。
两个数都对——"实付金额"算不算待支付和已取消的订单，题目没说。
限定已完成之后两种写法结果一致，因为已完成订单的 `pay_time` 全部非空。

### 61 题新基线

| 指标 | 50 题口径 | **61 题** |
|---|---|---|
| 首轮检索召回率 | 94%　63/67 | 93%　88/95 |
| **Schema 召回率（含兜底）** | 99%　66/67 | **97%　92/95** |
| 复核救回 | 11/150 | 14/183 |
| 执行准确率 | 89%　40/45 | 86%　48/56 |
| 陷阱题诚实率 | 100% | 100%　5/5 |
| **端到端准确率** | 90%　45/50 | **87%　53/61** |
| 单次分布 | 88%~90%，波动 1 题 | 84%~89%，波动 3 题 |

11 道新题拉掉 3 个点。但最值得看的不是端到端，是**Schema 召回率第一次掉破 100%**。

前 50 题里这个指标一直是 99%~100%，因为[全量复核](#拒答必须建立在完整信息上)
能捞回一切。现在有 3 个必中字段**连复核之后都没进 Prompt**：

```text
fact_order.order_status           E51
fact_user_behavior.behavior_type  E19
fact_refund.refund_amount         E27
```

捞不回的原因是**复核压根没被触发**——CoT 没说缺失。E51 的完整形态：

```sql
-- order_status 首轮没召回，CoT 没报缺失，复核没触发
-- 模型拿近义字段凑了一个：
... AND fact_order.finish_time IS NOT NULL    -- 用"有完成时间"代替"已完成"
→ 59436.98        参考答案 44149.54

降级记录: []      -- 一条告警都没有
```

这比 README 前面记的"嘴上承认、手上照编"更隐蔽：那个至少 CoT 里承认了缺失，
这个**什么都不说**，零告警地交出一个合理的错数字。

一个细节值得记：`fact_order` 的 12 个字段里有 **9 个**进了图，唯独筛选要用的
`order_status` 没进。**名额根本不缺，是筛选字段在自己表里输给了同表的兄弟。**
这否掉了"按表分散名额"这个方案——能救的只有按角色覆盖（筛选类关键词必须有
字段代表）。

### 失败构成：检索 3 道、生成 5 道

```text
检索侧（字段没进 Prompt）
  E51  0/3  上海店铺卖给北京用户的已完成订单金额    漏 fact_order.order_status
  E19  1/3  用户浏览行为的平均停留时长              漏 behavior_type
  E27  2/3  按店铺主营一级类目统计退款金额          漏 refund_amount

生成侧（召回全满，纯粹算错）
  E23  0/3  每个一级类目的商品成交金额              召回 3/3
  E37  0/3  转化率低于全店平均的店铺有多少家        召回 1/1
  E44  0/3  5月下旬比上旬的退款金额多多少          召回 2/2
  E59  0/3  两个不相连时间窗口的直播间订单数        召回 2/2
  E53  1/3  美妆护肤类目的加购次数                  召回 3/3
```

按考点看最弱的几类：

```text
区间对比        1/3  █░░
层级类目        2/4  ██░░
嵌套聚合        5/7  █████░░
多跳JOIN       9/12 █████████░░░

```

`区间对比` 3 题只过 1 题，而且 E44、E59 两道失败题**召回都是满的**——
这类的瓶颈明确在 SQL 生成，不在检索。以前只有 E44 一道题，说"区间对比弱"
拿不出样本；现在钉死了。

新增的「筛选与指标分表」过 7 道挂 2 道，headroom 有、诊断清楚、不是全过也不是全挂。
**这才是一把能称出差别的秤**——下一步做关键词覆盖约束时，靶子是明确的：
E51 能不能翻正、97% 的 Schema 召回能不能回到 99%、整体 87% 有没有回归。

### 关键词覆盖约束：秤补对之后，第一个测出真实收益的改动

秤补好了，回来解决 E24 暴露的那个根因：**精排逐字段打分，没有"这组字段合起来
能不能回答问题"的概念。**

没有去改精排，而是改了**名额分配**。因为代码里本来就埋着这个意图——

```python
dynamic_top_n = keyword_count * self.config.rerank_top_multiplier   # 2 × 6 = 12
```

名额是按"每个关键词分到 6 个"算出来的，但候选在 RRF 那一步被池化、全局排序，
于是一个关键词可以把 12 个名额全吃掉。所以这不是加新机制，
**是把公式已经假设的分配落实**。

现在有两条判据，分工清楚：

| 判据 | 问的问题 | 导向 |
|---|---|---|
| 断层（原有，逐字未动） | 这个词是不是**只可能**指这一个字段 | 精度 |
| 覆盖（新增） | 这个检索意图有没有**同级代表** | 召回 |

#### 关键设计点：代表必须和第一名同级

这条是两次实测逼出来的，两次都失败在"什么算代表"上。

**第一次，朴素覆盖（召回集有交集就算有代表）救不了 E24。**
『北京用户』的召回集里混着 `fact_order.user_id`（7.92 分），而它恰好入选了——
召回集每路 20 个、彼此重叠严重，只要沾一个就算覆盖，判据永远不触发。

**第二次，前 K 名覆盖救不了 E51。**摊开分数就明白了：

```text
『已完成订单』BM25
   fact_order.order_status    22.01           ← 真正要的字段，没入选
   fact_order.finish_time     10.09  已入选   ← 被当成了"代表"
   fact_refund.finish_time     9.60
```

入选的那个只有第一名的 **46%**，而它正是模型后来拿去凑答案的字段
（`finish_time IS NOT NULL` 代替"已完成"）。**沾边的近义字段不是代表，
只有同级的才是。**

同级用的是现成的 `dominant_keyword_tie_ratio`（0.85），没有再引入新阈值——
上一轮拍 `strong_ratio=2.0` 那种照着单个案例定参数的过拟合风险，这次避掉了。

#### 误差棒压下去之后，结论反了

repeat 3 时这个改动的账是"按题 −1、按次 +0.7"：端到端从 53/61 掉到 52/61，
但每轮均值反而上升。当时的判断是那 1 题来自 E27、E38 两道抖动题跌破 2/3 半数线。

**repeat 5 证实了这个判断**：两道题在 5 次投票下都站回正确的一侧，
端到端反而 +1 题。这是[单次运行有误差](#单次运行有误差用---repeat-压掉)
那一节的一个活例子——**差 1 题的对比，在 ±5% 的误差棒下根本不该下结论。**

#### 触发频率不是代价的度量

补回从 24 题次涨到 96 题次（305 次运行里三分之一触发），但稳定性没有恶化。
和上一轮"放开版"对照：

```text
放开版    补回 34 次   波动 1 题 → 7 题     端到端 −4pt
覆盖约束  补回 96 次   波动 2 题 → 2 题     端到端 +2pt
```

触发得更频繁，代价反而更小。差别在于补回的**是什么**：放开版塞的是"分数高的
字段"，覆盖约束塞的是"某个检索意图的最强代表"——前者是噪声，后者是缺失的拼图。

> 摊开才知道。逐题诊断之后，这 7 道里**没有一道是干净的 SQL 生成失败**：

### 召回全满，不等于生成错了

上一节的结论是"瓶颈转移到了生成"，准备去改 SQL 生成的 Prompt。动手前先做了一件
早该做的事：**把 7 道失败题的 CoT、SQL、实际结果和参考答案逐题摊开**。

| 题 | 表现 | 真正的原因 | 归属 |
|---|---|---|---|
| E59　0/5 | **答对了**（43 / 49） | 参考 SQL 给两段打的标签是我随手编的，字符串对不上 | 题目 |
| E36　2/5 | **答对了**店铺名 | 多返回一列比率，判分按整行比对 | 题目 |
| E37　0/5 | 每次口径不同 | "全店平均"有 5 种算法 | 题目 |
| E44　0/5 | 走错口径 | `dws_shop_daily.refund_amount` 按**下单日**归属，元数据写成"当日退款" | 元数据 |
| E23　0/5 | 0 行 | 不知道商品只挂二级类目 | 元数据 |
| E53　2/5 | 0 | 同上 | 元数据 |
| E19　2/5 | 答对了 | 检索边界抖动 | 检索 |

**7 道里没有一道是干净的 SQL 生成失败。**

#### 3 道是秤坏了

E37「转化率低于全店平均的店铺有多少家」最典型，5 种说得通的算法给出 5 个不同答案：

```text
店铺日均 vs 全部店-天平均         →   5   ← 参考答案
店铺日均 vs 各店日均的平均        →   7   ← "全店平均"最直白的读法
按买家数重算每店转化率 vs 全局    →  15   ← 业务上最正确（比率不该直接平均）
逐行比较，数的是店-天不是店       → 124
逐行比较后按店去重                →  15
```

模型每次挑一种，挑中第一种才算对。0/5 测的不是生成能力，是抛硬币。

E59 和 E36 是另一种坏法：**系统的答案是对的**，只是和参考答案长得不一样——
一个是标签字符串，一个是多了一列。这正是[判分方式](#判分方式)里那条规矩：
输出不明确的题目没法客观判分。E59 是我这一轮自己出的题，又踩了一次。

#### 3 道是元数据说错了或没说全

**E44 的元数据是错的**。`dws_shop_daily.refund_amount` 的生成逻辑是：

```sql
SELECT SUM(r.refund_amount) FROM fact_refund r
JOIN fact_order ro ON ro.order_id = r.order_id
WHERE ro.shop_id = o.shop_id
  AND DATE(ro.create_time) = DATE(o.create_time)   -- 按订单的下单日期归属
```

某天的值是"那天下的订单后来产生的退款"，不是"那天发生的退款"。全量合计和
`fact_refund` 分毫不差（都是 917767.25），按日期切分就完全是两个数。
元数据却写着"店铺当日退款金额合计"——模型照着描述选了它，错的是描述。

**E23、E53 的元数据没说全**。元数据写了"两级类目结构"，但从没说**商品只挂在
二级类目上**——`dim_product.category_id` 的描述只有"商品所属类目ID"。模型合理地
假设商品能直接挂一级类目，拿"美妆护肤"去关联，结果永远是空的。

#### 一个没应验的假设

诊断前我提过一个假设：SQL 生成那一步看不到用户原始问题，只看 CoT 的转述，
可能丢细节。**7 份 trace 里一次都没应验**——CoT 把日期边界、双窗口都传得很完整，
E23、E53 的错误是 CoT 那一步就犯下的。记下来，免得以后再去修一个不存在的问题。

#### 修法与重测

- **4 道题改问法**：E59 改问差值（答案收敛成一个数）、E36 加"只返回店铺名称"、
  E37 写死两个"平均"各是什么、E44 加"按退款申请时间算"
- **2 处元数据**：`dws_shop_daily` 的表、`stat_date`、`refund_amount` 写明按下单日期归属；
  `dim_product.category_id`、`dim_category.parent_category_id` 写明只挂二级类目、要自关联上卷

E44 那条是修完元数据才暴露的：模型改用 `fact_refund` 之后，"5 月下旬的退款"
按申请时间是 268979.27、按完成时间是 269772.91，又是一层分叉。

每道改过的题，note 里都记了原问法为什么没法判分、实测几种口径各得多少——
改题要有"系统答案在合理读法下是对的"作为证据，不然就是挪球门。

#### 真正的 SQL 生成缺陷，终于出现了

修完元数据，E44 的模型选对了 `fact_refund.apply_time`，然后暴露出这一轮诊断里
**第一个干净的、系统性的生成缺陷**：

```text
5 次里 4 次:  apply_time BETWEEN '2024-05-01' AND '2024-05-10'   → 241871.02  ❌
5 次里 1 次:  上界写成次日 '2024-05-11'                          → 268979.27  ✅
```

`apply_time` 是带时分秒的 TEXT（`'2024-05-10 20:25:00'`），裸 `BETWEEN` 是字符串比较，
**每个窗口的最后一天 00:00 之后全部被排除**。Prompt 里的样例值明明带着时分秒，
模型没用上这个信息。

E59 对同一个坑同样敏感：正确写法得 6，丢掉两个窗口最后一天（5/30 有 8 单、
5/7 有 6 单）得 4。它 3/5 勉强过线，失败的那 2 次和这个坑吻合。

这才是"改 SQL 生成"该改的地方，下一步做。

### SQL 生成看不到样例值

E44 那个日期边界的坑，查下去根因比"模型没用上样例值"更直接：**SQL 生成那一步
根本看不到样例值。**

检索阶段抽了样例值，CoT 阶段的 Prompt 里也有；但转成 SQL 生成用的局部 Schema 时，
`LocalSchemaStore.from_schema_graph` 只拷了字段名、描述、类型三样。SQL 模型眼里的
`apply_time` 是这样的：

```text
- apply_time：退款申请时间。，TEXT
```

一个 TEXT 字段，看不出里面存的是 `2024-05-10` 还是 `2024-05-10 20:25:00`。
写裸 `BETWEEN` 是在信息缺失下的合理猜测，那 1 次写对是蒙的。

[上一节](#一个没应验的假设)记过一个没应验的假设："SQL 生成看不到原始问题会丢细节"。
7 份 trace 里一次都没应验——但它的近亲，**"SQL 生成看不到样例值"**，是对的。

改了两处：

- **信息管道**：`TableColumn` 加 `samples`，从 SchemaGraph 拷前 3 个样例值，
  渲染成 `- apply_time：退款申请时间。，TEXT；样例值：2024-06-03 01:37:00、…`。
  三个就够看出格式，再多只是堆 token
- **日期规则**（生成和修正两个 Prompt 都加）：样例值带时分秒的字段，按日期筛选写成
  `DATE(字段) BETWEEN` 或左闭右开 `字段 >= 起始日 AND 字段 < 结束日次日`；
  日期字面量一律 `'YYYY-MM-DD'`，年份以样例值为准

两处缺一不可：只有规则，模型没法判断字段带不带时分秒；只有样例值，
LLM 看见时间戳照样常写裸 `BETWEEN`。E44 单题 5 次：**改前 1/5，改后 5/5**，
全部写成 `DATE(apply_time) BETWEEN`。

同一轮把另外 6 道暴露在"多返回一列"判分问题下的题也改了问法，和 E36 保持一致：
E28、E30、E38、E39、E43、E45 各加一句"只返回 X"。

repeat 5 全量：

| 执行准确率 | 95%　53/56 | **98%　55/56** |
| **端到端准确率** | 95%　58/61 | **98%　60/61** |
| 单次分布 | 93%~98%，波动 3 题 | **97%~98%，波动 1 题** |
| 抖动题 | 6 道 | 3 道 |

```text

改问法（尺子校正）     E39 2→5   E38 4→5
抖动                  E23 4→5   E35 5→4   E55 5→4（多数票都不变）
```

样例值对所有题的 SQL 生成都可见了，这是个面很宽的改动——**其余题没有任何多数票回归**。

### 堵住零告警：筛选值守卫

到 98% 时只剩一道失败题 E19「用户浏览行为的平均停留时长」，而它和 E51 是同一种
最危险的形态——**零告警的错答案**：

```text
E19  behavior_type 没召回 → CoT 不觉得缺什么 → SELECT AVG(stay_seconds) FROM fact_user_behavior
     → 300.47（参考 296.02），降级记录为空
E51  order_status 没召回 → 模型拿 finish_time IS NOT NULL 凑"已完成"
     → 59436.98（参考 44149.54），降级记录为空
```

[全量复核](#拒答必须建立在完整信息上)救不了它们：复核只在 CoT **自己说缺失**时触发，
而这两次 CoT 根本没意识到缺了什么。缺的是一个不依赖 CoT 自觉的检查。

#### 拿数据库当裁判

「浏览」「已完成」「北京」恰好是某些字段的**枚举取值**，库里查得到。所以
[filter_guard.py](askdata_pipeline/filter_guard.py) 做的事很简单：

1. 建链路时扫一遍库，把低基数文本字段（去重取值 ≤ 50）的取值建成索引。
   单字取值（男 / 女）不收，在中文问句里太容易误撞；英文取值要求词边界
2. SQL 跑完后，找出问题里提到的取值（长的优先、不重叠）
3. SQL 里**既没有这个取值、也没出现它所属字段的字段名**，就判定筛选被丢了

第 3 条的判据刻意放得很宽：碰了所属字段就算用上，容忍 `order_status IN (...)`、
`order_status <> '待支付'` 这类换写法的筛选，只抓整个条件消失的情况。
整个检查是确定性的，不调 LLM。

检出后带提示用全量 Schema 重规划一次；重规划后还丢，就不再重试，结果照交但留下
`FILTER_VALUE_DROPPED`——目标是**不再零告警**，不是保证每次都救回来。

#### 接进链路之前，先离线验证

拿题库里所有参考 SQL 当"正确答案"跑一遍，任何被标记的都是误报；
再拿抓到的两条错 SQL 验证能不能检出。这一步不花 API：

```text
ecommerce 参考 SQL   误报 3 / 56   E05、E07、E53
chinook   参考 SQL   误报 0 / 13
E19 错 SQL          检出「浏览」（fact_user_behavior.behavior_type）
E51 错 SQL          检出「已完成」（fact_order.order_status）——"上海""北京"都用上了，没误标
```

E07、E53 的误报只针对参考 SQL 的写法：它们用 `category_id = 1` 按 ID 过滤一级类目，
没出现类目名。模型实际生成的 SQL 几乎都写 `category_name = '美妆护肤'`，接受。

**E05 不是误报，是题库自相矛盾：**

```text
E05  "所有已支付订单的实付金额合计"
     参考答案按 pay_time IS NOT NULL（付过款就算）   → 9043512.50
     按 order_status = '已支付'（字面取值）          → 1551020.05
```

而 E51 把"已完成订单"读成 `order_status = '已完成'`。**同一种措辞，两道题往相反
方向解读了**——E51 失败时的 `finish_time IS NOT NULL` 和 E05 参考答案的
`pay_time IS NOT NULL` 结构上一模一样，任何检查都分不开。守卫要是按字面去纠正，
会把 E05 从对的改成错的。

所以先给题库定一个约定：**问题里出现枚举取值原文，就按那个取值筛选**。
E05 要表达"付过款"，就不该用"已支付"这个原文，改成
"所有付过款的订单（不论后来是否完成或退款）"。

#### 重规划的提示不下命令

提示只摆事实——「浏览」是 `fact_user_behavior.behavior_type` 的取值，上一次的 SQL
没体现这个条件，请重新判断是否要按它筛选。不写"必须按它筛选"。

原因还是 E05 那类情况：真实用户说"已支付订单"，可能真是指付过款的订单。
硬塞一个取值筛选会把对的改成错的；摆出事实让模型自己判断，最坏也就是维持原判。

#### 结果

E19 定向探测 5 次：**守卫触发 4 次、救回 4 次**，另 1 次首次规划就写对了，守卫没多管。

全量 repeat 5：

```text
dict(row)  : {'FirstName': 'Nancy', 'LastName': 'Edwards'}    ← 上级的名字没了
```

### 同名列被合并：执行层和裁判的同一个坑

HB14 暴露的问题：执行器用 `dict(row)` 把结果行转成字典，SELECT 里有同名列时
（自关联最常见），同名的键互相覆盖，**用户只能看到半张表**。评测器算参考答案时
用的是同一个写法。

修法是列名去重（重名的依次加 `_2`、`_3`，一直加到不和任何已有列名冲突为止），
再**按位置**把值填进去，列名从 `cursor.description` 取。执行器和评测器共用
`mcp_router.sqlite_executor.unique_column_names`：

```text
SELECT e.FirstName, e.LastName, m.FirstName, m.LastName ...
修复前  {'FirstName': 'Nancy', 'LastName': 'Edwards'}
修复后  {'FirstName': 'Nancy', 'LastName': 'Edwards', 'FirstName_2': 'Andrew', 'LastName_2': 'Adams'}
```

没有同名列的查询，结果和原来**逐字相同**，所以这个修复不会改变其他任何题的判分。
顺带一个改善：0 行的结果也能拿到列名了（原先是从第一行取，没有行就是空）。

新增 8 个测试。为了确认测试真的守得住这个 bug，做了一次变异测试：保留新函数，
只把按位置填值改回"用原始列名建字典"，2 个测试当场失败。

HB14 修复后 0/3 → **3/3**。这是修 bug 的结果，**不是泛化证据**——第二套题已经用过了。

还有一个想到的裁判局限，先记下不改：判分时每行的值会先排序再比，为的是容忍列顺序
不同。代价是在 HB14 这种题上，把员工和上级的名字对调也照样判对——裁判分不出
哪个名字属于哪个角色。

`time_coverage` 的断言——它不进任何文本，往返时丢了，原有的文本比对发现不了。
变异测试：把覆盖年份改回写进 `value_range`，13 个测试失败。

### 整数相除，和跨表比例

第三套 450 次运行失败 29 次，**全在检索给齐字段之后**——首轮检索漏召回的 9 次全是 H3C11
的关联键，都被复核接住。瓶颈已经从检索转到了生成。失败最多的两道题占了一半：H3E13
（9/9，筛选值守卫误报，见上文）和 H3E14（6/9）：

```sql
ROUND(SUM(COALESCE(total_order_count, 0)) / COUNT(user_id), 3)   -- 两个整数相除，SQLite 截断成整数
```

扫了手头 1455 次运行的 SQL：93 条带除法，模型多数时候自己会写 `* 1.0`、`100.0` 或用 `AVG()`。
完全没转浮点的只有三道题——E36、E57 除的是金额，本来就是浮点，全对；H3E14 是两个整数聚合
相除，全错。

#### 一条规则，引出另一个坑

写了 12 道探针（不来自任何留出集），刻意覆盖"整数总和 ÷ 个数"的问法——人均、平均每、
占比、百分之多少——每道都先确认按整数除法算出来的答案一定不同。在 SQL 生成规则里加一条：
两个整数相除会截断，算平均值、比例时被除数乘以 1.0。

| | 规则前 | 只写整数除法 | 示例换成中性的 | 加"各自用子查询" |
|---|---|---|---|---|
| 13 道探针（含 H3E14） | 29/39 | 35/39 | 35/39 | **39/39** |

整数除法全修好了，可 P08、P10 变差："发票总数 ÷ 客户总数"被写成
`COUNT(a) * 1.0 / COUNT(b) FROM A, B`——两张表一连接，分子分母数的都是连接后的行数，
答案成了 1.0。规则前 P10 三次都用子查询分别计数；一提醒要算比例，模型就倾向在一个
SELECT 里算完，示例换成中性的也一样。于是补了后半句：分子分母来自不同的表时，
各自用子查询算好再相除。

#### 后半句是看着失败加的，另写一批验证

第二批 8 道探针在选定措辞之后才写，一半是"A 表总数 ÷ B 表总数"：**18/24 → 24/24**。
规则前错的主要是分母——"专辑总数 ÷ 艺术家总数"，分母只数了有专辑的艺术家，算出 1.7
而不是 1.26——后半句把这类错一并解决了。两批合计 47/63 → **63/63**。

#### 回归：E30 是尺子的问题

| 指标 | 规则前（只留保底那轮） | 加规则 |
|---|---|---|
| ecommerce 端到端（61 × 5） | 61/61 | 60/61 |
| 305 次运行中通过 | 301 | 300 |
| 去掉 E30，其余 60 题 | 297/300 | 299/300 |
| Chinook 端到端（15 × 3） | 15/15 | 15/15 |

ecommerce 唯一的失败是 E30（1/5）。失败的 4 次 SQL 逻辑都对，差别只在第 3 名——第 3 名有
4 个商品并列 15 次，判分只认参考 SQL 取的那一个。加了规则，模型换了一种同样正确的写法，
SQLite 对并列行的排法跟着变了。E30 已改成前两个（`c401d21`，算尺子校正），新 E30 在加规则
后 5/5；去掉 E30，其余 60 题没有回归。

新增测试：生成和修正两份提示词里都要有这两条规则——改规则时最容易漏掉修正那一份。

两批探针都是对着这个问题写的；规则在陌生题上灵不灵，要等第四套盲写题。

### 题目自带口径的取值，守卫不再查

H3E13 当时记下没修。回头把守卫在全部 191 道题的参考 SQL 上跑了一遍——当初离线验证只跑了
主题库——留出集上被标记的不止它一道：

```text
H3E13  已支付过的订单（支付时间不为空）……
H3E18  当天已支付买家数 ÷ 当天下单买家数；……已支付买家指……支付时间不为空的买家
H3E21  只算已支付订单（支付时间不为空，包括后来退款的订单）
H3C01  单位 MB（1 MB 按 1048576 字节计）
H18    只算付过款的订单（已支付、已完成、已退款都算）    ← 参考 SQL 走的汇总表，模型写 IN (...) 不会被标
```

前四道是同一个规律：**题目自己给了口径**。参考 SQL 按口径写成 `pay_time IS NOT NULL`，
守卫看不到"已支付"，就要模型补 `order_status = '已支付'`。

SQL 这一侧分不开对错：E51 那条错 SQL（`finish_time IS NOT NULL` 凑"已完成"）和 H3E13 的
对 SQL 结构一模一样。能分开它们的只有问题本身——E51 没给口径，H3E13 给了。

#### 修法

取值后面紧跟着口径说明，这个取值就不查：中间最多隔 4 个字、不跨标点，然后是括号或
"指 / 即 / 定义为"。口径在任何一处下了，对整道题都有效——H3E18 先说"已支付买家数"，
隔一句才下定义。

不跨标点是为了不误伤 E55"上海店铺的销售额，减去上旬（1日到10日）"：括号说的是上旬，
上海照样要查。

191 道题逐题比较守卫要查的取值，186 道和改前**完全相同**，包括主题库全部 76 道——所以
主题库的端到端不用重跑，守卫在那里的行为一个字没变。变了的 5 道：

| 题 | 改前要查 | 改后 | |
|---|---|---|---|
| H3E13、H3E18、H3E21 | 已支付 | — | 目标 |
| H3C01 | MB | — | 单位，本来就不是筛选 |
| H3E27 | 加购 | — | **代价** |

H3E27 是"……最早一次加购的时间（订单状态不限）"：括号说的是订单状态，和加购无关，
字面上分不出来。参考 SQL 改前改后都没被标，所以代价是这道题少一层兜底，不是把对的改错。
同理，"北京（买家所在地）的订单"这种括号只是指明字段、仍要按取值筛选的，也会跳过检查。

#### 对照：同一份代码，只差这一处

在当前 HEAD 上开一个副本跑改前，每题 repeat 3：

| 题 | 改前 | 改后 |
|---|---|---|
| H3E13 | 0/3，守卫触发 3 次 | **3/3**，0 次 |
| H3E18 | 0/3，守卫触发 3 次 | **3/3**，0 次 |
| H3E21 | 3/3，守卫触发 5 次 | 3/3，0 次 |
| 平均耗时 | 21.2s / 50.0s / 54.7s | 14.0s / 19.2s / 20.8s |

H3E13 当时说"很可能是守卫推错的"，现在坐实了。**H3E18 是新发现**：第三套里它从删精排前的 0/3
变成删后的 2/3，算在了删精排文本的账上；现在看，它失败的那些次里至少有一部分是守卫的误报。H3E21 没错，
但每次多一轮全量重规划，耗时翻了一倍多。

新增 4 个测试。变异测试：去掉口径豁免 2 个失败，"任何一处"改回"每一处" 1 个失败，
允许跨标点 1 个失败。

这三道题是诊断来源，对它们的翻正只算对症，不算泛化——第三套早已用过。

## 结果校验与回调修正 · 自洽性投票

原作者在 README 里标注「暂不包含结果校验与回调修正」，这是补上的那一块。
两个机制都可配置，**但都不该记在"准确率提升"账上**，原因见下。

```python
PipelineConfig(
    sql_repair_attempts=1,      # SQL 执行失败时把报错喂回模型重生成
    self_consistency_runs=1,    # 1 = 关闭；N = 跑 N 次按执行结果取多数
)
```

评测器也带上了对应开关：

```bash
python -m eval.runner --repeat 3 --self-consistency 3 --repair 1
```

### 回调修正：功能补上了，但当前无事可做

执行器的报错是一手信息——`no such column: fact_order.category_id`
直接点名了问题所在，比让模型凭空重想一遍有效得多。

但实测 `SQL_REPAIRED` 一次都没触发。最近一轮全量评测的失败构成是
「结果不符 5 题」，**零个 SQL 报错**——早先那些 `no such table`、
`no such column` 在前几轮已经被修掉了（库名前缀剥除、全量 Schema 复核）。

**它现在是保险不是修复**，换新库、换模型时才会派上用场。

### 自洽性投票：数学上有前提，当前净效果为零

先说为什么需要它。裸调 API，同一个 prompt、`temperature=0`，
DeepSeek 4 次给出 **4 种不同输出**，thinking 开关无关：

```text
1. 数据库索引是一种以额外存储和写入开销为代价、通过预排序的数据结构（如B+树）将查询…
2. 数据库索引是一种以额外存储和写入开销为代价、通过预排序的数据结构（如B+树或哈希表）…
3. 数据库索引是一种以额外存储和写入开销为代价、通过预排序的数据结构（如B+树）加速…
4. …
```

这不是本项目的 bug，是 LLM 推理服务的固有性质：
`temperature=0` 只保证贪心解码，不保证跨请求确定性。

**但多数投票只在单次正确率 > 50% 时才有增益**，低于 50% 时它会放大错误答案。
6 道嵌套聚合题的 A/B 对比逐题验证了这一点：

| 题 | 单次正确率 | 投票关闭 | 投票 3 次 |
|---|---|---|---|
| E33 / E34 / E40 | ~100% | 3/3 | 3/3 |
| E35 | ~67% | 2/3 | **3/3** ↑ |
| E37 | ~33% | 1/3 | **0/3** ↓ |
| E36 | ~0% | 0/3 | 1/3 |
| **总计** | | **4/6** | **4/6** |

推上去一道，压下去一道，**净效果精确为零，成本却是 2.7 倍**
（每题 12s → 32s）。所以默认关闭。

它在两种情况下值得开：模型换成更强的（单次正确率整体上移过 50%），
或者对"错了代价很大"的问题单独开启，用成本换确定性。

`SELF_CONSISTENCY_DISAGREEMENT` 这个降级码本身有价值——
它精确标出了哪些问题模型自己都拿不准。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 供应商、数据集规模、降级状态 |

## Schema 索引接进主链路

原本 `schema_indexing` 建好 Milvus 三级索引，主链路却每次启动重扫源库——
**模块从没被接进来过**。现在补上了：

```python
HybridSchemaRetrievalService.from_milvus(
    uri="runtime_data/schema_index.db",
    embedding_client=..., rerank_client=...,
)
```

### 先说清楚：当前规模下没有性能收益

动手前先量了一遍启动耗时，结果推翻了我原本的理由：

```text
建库 + 扫 Schema + 编码      0.36s     ← 我以为的瓶颈
载入两个 bge 模型            14.98s    ← 真正的瓶颈（98%）
```

索引能省的只有那 0.36 秒，而查询时还要用 bge 编码 query、用 reranker 精排，
**模型必须加载，一秒都省不掉**。

它的价值在别处：**规模**（81 个字段编码 0.33 秒，8100 个就是 33 秒）、
**解耦**（换库加库不用重扫）、**共享**（多个查询进程共用一份索引，而不是各建各的）。
这些在 Demo 规模上都体现不出来。

### 接的过程挖出三层问题

**一、索引不是自包含的。**只存了 9 个标量字段，而 `ColumnSchema` 有 17 个。
缺的正是 `description`、`aliases`、`samples`、`business_usage`、`value_range`——
**恰恰是渲染进 CoT 和 SQL 提示词的业务语义**。照现状接进去，链路照样能跑，
提示词却悄悄退化成只剩字段名和类型。修法是把完整的 `ColumnSchema` 与 `TableSchema`
序列化成 JSON 一并存入。

**二、两个模块各有一份 `TableRelation`。**字段完全相同，但只有 `schema_indexing`
那份带 `join_condition` 和 `relation_key` 两个 property——**字段一样、行为不一样，
类型看着兼容，一调就炸**。改成鸭子类型取值，取不到就按关联键现拼。

**三、两个模块各实现了一套三级索引文本构建。**产出的文本 **81 个字段全都不一样**。
这条最要命：光接上不校验的话，检索结果会悄悄漂移。

第三条也决定了架构上谁是权威——**检索服务那一套**，因为只有它会读取
`business_meta` 里手写的 21 条 `keyword_text` 和 15 条 `rerank_text`，
而那些手写文本是这个项目最值钱的资产。所以索引的职责是
**持久化检索服务的产出**，而不是自己再造一遍：

```python
builder.build(columns=..., relations=..., tables=..., documents=service.documents)
```

### 验证：不是"能加载"，而是"加载出来一模一样"

```text
keyword_text   不一致 0 个
vector_text    不一致 0 个
rerank_text    不一致 0 个
向量最大差异    0.00e+00

4/4 条查询的提示词上下文逐字节一致
```

这条断言写进了 [tests/test_diagnostics.py](tests/test_diagnostics.py)
的 `SchemaIndexRoundTripTestCase`。只断言"能加载"是不够的——
**加载成功但内容退化，正是这个项目反复踩的那类静默失败。**
