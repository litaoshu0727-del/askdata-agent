# AskData Text2SQL Demo

本项目演示从自然语言 Query 到 SQL 生成与执行的端到端流程。

> **关于来源**
>
> 基线代码（Schema 索引、两阶段检索、CoT 规划、SQL 生成、MCP 路由、长短期记忆）
> 来自公开分享的 AskData 项目压缩包，版权归原作者所有，本仓库仅用于学习与二次开发。
>
> 本仓库在其上新增：macOS 环境适配、供应商解耦与 DeepSeek 接入、
> 本地 bge 向量与精排、11 表 81 字段的电商数据集、指代消解与多轮追问、
> 静默降级告警与回归测试。详见 [docs/排查记录.md](docs/排查记录.md)。

## 当前链路

```text
用户Query
  ↓
关键词抽取
  ↓
Schema混合检索 + RRF + Rerank
  ↓
SchemaGraph
  ↓
CoT四元组规划
  ↓
SQL生成
  ↓
MCP路由执行
  ↓
查询结果
```

动态路由会先结合长短期记忆判断用户意图：需要新业务数据时进入上述 Text2SQL 链路；结果解释、指标说明、历史结果追问和业务知识问答进入 `data_qa` 链路，不执行数据库查询。

路由实现位于 `askdata_pipeline/routing.py`，统一编排入口位于 `askdata_pipeline/dynamic_service.py`，对话问答实现位于 `askdata_pipeline/data_qa.py`。

暂不包含结果校验与回调修正。

DeepSeek 只提供 Chat 接口，没有 Embedding、也没有 Rerank 服务，

| 关键词抽取 | DeepSeek | OpenAI 兼容格式，零改造 |
| CoT 四元组规划 | DeepSeek | 开启 thinking 模式 |

### 关于 thinking 模式

DeepSeek 默认开启思考模式，而**思考模式下 `temperature` 参数会被忽略**。
项目按场景分别处理：

- CoT 四元组规划：显式开启思考（`thinking.type = enabled`），这本来就是推理场景
- SQL 生成、关键词抽取：显式关闭思考，让 `temperature=0.0` 真正生效，保证输出确定性

### 不配置任何 Key 时

行为与改造前完全一致：CoT 与 SQL 走 Mock，向量用本地哈希伪向量，精排用规则排序。
Demo 秒开，不下载任何模型。

## 电商数据集

原始的 `trade` 数据集只有 2 张表 9 个字段，随便召回几个字段就全命中了，
两阶段检索这套机制其实没派上用场。`ecommerce` 数据集用来补这一课。

### 规模

| 分层 | 表 | 说明 |
|---|---|---|
| dim | `dim_user` `dim_shop` `dim_product` `dim_category` | 用户、店铺、商品、类目 |
| fact | `fact_order` `fact_order_item` `fact_payment` `fact_refund` `fact_user_behavior` | 订单、明细、支付、退款、行为 |
| dws | `dws_user_summary` `dws_shop_daily` | 用户累计指标、店铺日报 |

合计 11 张表、81 个字段、约 7000 行数据，固定随机种子生成，每次结果一致。
dws 汇总层由事实表聚合而来，`SUM(dws_shop_daily.gmv)` 与 `SUM(fact_order.order_amount)` 严格相等。

### 刻意埋的坑

这套 Schema 专门设计了几组近义字段，用来检验检索的区分能力：

- **9 个金额字段**：`order_amount`（订单原价）、`pay_amount`（实付）、`discount_amount`（优惠）、
  `freight_amount`（运费）、`refund_amount`（退款）、`item_amount`（明细）、
  `gmv`（成交总额）、`total_pay_amount`（累计实付）、`avg_order_amount`（客单价）
- **`pay_amount` 在两张表里都有**：`fact_order` 里是订单实付，`fact_payment` 里是支付流水
- **`city` 在两张表里都有**：`dim_user.city` 是买家所在地，`dim_shop.city` 是店铺经营地
- **`finish_time` 在两张表里都有**：订单里是确认收货，退款里是退款到账
- **纯业务口径词**：用户说“客单价”“销售额”，字段名叫 `avg_order_amount`、`gmv`，字面零重合

```bash
python -m askdata_pipeline.ecommerce_demo --query "客单价最高的10个用户是谁"
```

### 检索参数要随 Schema 规模放大

`rerank_top_n = 关键词数 × rerank_top_multiplier`。默认的 multiplier=2 对 9 个字段的
trade 库够用，但在 81 个字段上，2 个关键词只保留 4 个字段，必然漏召回。
`text2sql_pipeline._build_retrieval_config()` 里按数据集分开配置：
ecommerce 用 multiplier=6、min_top_n=10、max_top_n=30、RRF final_top_k=60。

**这是把 Demo 搬到真实库时最容易踩的坑**——链路没报错，只是悄悄少给了几个字段，
表现为模型说“Schema 里没有这个字段”。

### 换成你自己的库

照着 [ecommerce_data.py](askdata_pipeline/ecommerce_data.py) 改三处：

1. `sql/create_*.sql` 换成你的建表语句，**外键一定要声明**，表关系是靠它自动提取的
2. `get_*_business_meta()` 写字段的业务含义和别名——这份元数据的质量直接决定召回准确率
3. `_prepare_dataset()` 里加一个分支

元数据里最值钱的是 `aliases` 和近义字段的辨析：把业务口头怎么说、这个字段和那个字段差在哪
写清楚，检索准确率的提升比换更大的模型明显得多。

这句话在一个**不是我设计的库**上做过消融验证——首轮检索召回率 50% → 94%，
见 [Chinook 元数据消融](#元数据消融把元数据整份拔掉)。

## 静默降级告警

这个项目最难发现的不是报错，是「链路跑通、退出码 0、输出看着合理，
但中间某一环已经悄悄失效了」。三个真实案例见 [docs/排查记录.md](docs/排查记录.md)。

[askdata_diagnostics.py](askdata_diagnostics.py) 给每一处已知的降级点装了探针：
出问题时要么在 stderr 留下一行告警，要么被 `PipelineResult.diagnostics` 带出来。

### 降级码

| Code | 含义 | 后果 |
|---|---|---|
| `COT_PARSE_EMPTY` | CoT 有输出但没解析出四元组 | **一条 SQL 都不会生成**，链路安静停住 |
| `SCHEMA_RECALL_CAPPED` | 精排名额相对候选数过小 | 可能已截掉需要的字段，模型会说「Schema 里没这个字段」 |
| `MODEL_MOCK_FALLBACK` | 没 Key，CoT / SQL 走写死的 Mock | 换任何非内置 Query 都会返回缺失或 `SELECT 1` |
| `RERANK_MOCK_FALLBACK` | 没 Rerank 服务，精排走规则排序 | 只覆盖内置词表，没有通用语义判断 |
| `EMBEDDING_MOCK_FALLBACK` | 向量是哈希伪向量 | 语义召回实际失效，只剩字面匹配 |
| `COLUMN_SAMPLES_FAILED` | 字段样例值抽取失败 | 索引文本少一块语义，召回质量下降 |

### 怎么看

Demo 会在最后集中展示：

```text
9. 本次运行的降级记录
共 4 条。结果看着正常，但以下环节实际已经打了折扣：

  ⚠️  [EMBEDDING_MOCK_FALLBACK] 当前使用本地哈希伪向量，没有真实语义能力……
  ⚠️  [MODEL_MOCK_FALLBACK] 未配置 API Key，CoT 规划降级为写死的 Mock 结果……
```

配好 DeepSeek + 本地 bge 之后应该是：

```text
【6】降级记录
    无降级，链路每一环都在满配置下跑完
```

代码里读：

```python
result = pipeline.run(query)

if result.diagnostics:
    for item in result.diagnostics:
        print(item.render())
```

自己的代码里收集：

```python
from askdata_diagnostics import collect

with collect() as diagnostics:
    ...  # 跑链路
```

`collect()` 基于 `contextvars`，只覆盖当前执行上下文。
后台线程（例如记忆模块的异步摘要）里的降级仍然会写 logging，但不进 `collect()` 列表。

### 回归守卫

[tests/test_diagnostics.py](tests/test_diagnostics.py) 里有两条测试直接对应排查记录里的问题：

- `test_punctuation_variants_all_parse` —— 锁死 CoT 四元组在句号、半角逗号、全角逗号、无标点四种写法下都能解析
- `test_narrow_config_emits_recall_capped` —— 把精排参数调回出事前的值，断言告警必须触发；
  当前参数下断言不触发

这两条保证同样的 bug 不会再悄悄回来。

## 多轮追问

单轮问答只考验 Text2SQL，多轮真正难的是**指代消解**：
用户第二句说「它们的退款金额呢」，「它们」指的是上一轮 SQL 查出来的那三家店铺——
这个信息不在当前 Query 里，只存在于会话记忆中。

```bash
python -m askdata_pipeline.multi_turn_demo
```

五轮对话覆盖四种典型形态：

| 轮次 | 问题 | 路由 | 查库 | 考点 |
|---|---|---|---|---|
| 1 | 销售额最高的三个店铺是哪些 | `database_query` | 是 | 基线，纯 Text2SQL |
| 2 | 它们的退款金额分别是多少 | `database_query` | 是 | 指代消解 + 新数据需求 |
| 3 | 刚才第一名的店铺叫什么名字 | `data_qa` | 否 | 复用历史结果，不打数据库 |
| 4 | 客单价这个指标是怎么算的 | `data_qa` | 否 | 指标口径问答 |
| 5 | 帮我查一下这些店铺的买家数 | `database_query` | 是 | 指代对象已滑出短期窗口 |

### 指代消解是独立的一步

把会话记忆拼在 Query 前面一起送进 CoT，指望模型顺手解决——实测不行，两种失败都会出现：

- **关键词抽取拿到的是原始 Query**，把「它们」当成了检索词，真正的指代对象根本没进检索
- **CoT 看到了上下文但没被要求先解指代**，结果要么忽略限定条件查了全表，
  要么从店铺名「臻品自营店15」里抠出数字 15 当成 `shop_id`，凭空造出一个过滤条件

所以 [query_rewriter.py](askdata_pipeline/query_rewriter.py) 把它拆成显式的一步，
放在关键词抽取**之前**：

```text
用户：它们的退款金额分别是多少
  ↓ 指代消解
销售额最高的三个店铺"臻品自营店15""优选旗舰店1""旗舰旗舰店7"的退款金额分别是多少
  ↓ 关键词抽取
销售额，店铺，臻品自营店15，优选旗舰店1，旗舰旗舰店7，退款金额
  ↓ SQL
WHERE dim_shop.shop_name IN ('臻品自营店15', '优选旗舰店1', '旗舰旗舰店7')
```

改写 Prompt 里有一条专门约束：**绝对不要凭空推断任何 ID**。
店铺名叫「臻品自营店15」不代表它的 ID 是 15——这是实测中模型真实犯过的错。

只有检测到指代词（它们、这些、刚才、上述……）才会调模型，自包含的问题直接短路，
不浪费一次调用。

### 指标口径问答要看得见 Schema

`data_qa` 原本只拿得到会话记忆，问「客单价怎么算的」只能回答「上下文里没有定义」。
但 `dws_user_summary.avg_order_amount` 的元数据里明明写着「业务上叫客单价」。

`build_metric_glossary()` 把 `business_meta` 压成一份指标口径表喂给 `data_qa`，
现在能直接定位到表名、字段名和业务含义。

### 相关降级码

| Code | 触发条件 |
|---|---|
| `QUERY_REWRITE_SKIPPED` | 检测到指代词但没 Key，多轮追问结果大概率不正确 |
| `QUERY_REWRITE_FAILED` | 指代消解调用失败，已回退为原始 Query |
| `EMPTY_RESULT_SET` | SQL 执行成功但返回 0 行，筛选条件可能有问题 |

`EMPTY_RESULT_SET` 就是为幻觉 ID 这类问题准备的——
`WHERE shop_id IN (15, 1, 7)` 不会报错，只会安静地返回 0 行。

## 评测

```bash
python -m eval.runner                  # 跑全部 50 题
python -m eval.runner --case E36       # 只跑一道
python -m eval.runner --tag 嵌套聚合    # 只跑某类考点

python -m eval.runner --dataset chinook --meta ab --repeat 3   # 外部库 + 元数据消融
```

### 为什么需要它

在有评测集之前，每次改动都是「跑一条 Query 看对不对」。这带来两个问题：

- **没法回答"提升了多少"。**元数据写得再细，也只能说「感觉准了」。
- **bug 是撞见的，不是测出来的。**曾经有一个 SQL 表名前缀的 bug，
  同一道题连过两轮、第三轮才挂——手跑单条 Query 有 2/3 的概率看不见它。

### 三个指标分开统计

| 指标 | 衡量什么 | 定位到 |
|---|---|---|
| 首轮检索召回率 | 检索这一轮就召回了，没靠兜底 | 检索环节 |
| Schema 召回率 | 最终进 Prompt 的 Schema 里有没有 | 检索环节 + 兜底 |
| 执行准确率 | 结果集与参考答案是否一致 | 生成环节 |
| 陷阱题诚实率 | Schema 支撑不了时会不会编 | 可靠性 |
| 端到端准确率 | 整条链路 | 总分 |

前两个的差就是[全量 Schema 复核](#拒答必须建立在完整信息上)兜掉的量。
只看第二个会漏掉检索的真实水平——这个坑的完整经过见
[元数据消融](#先得修尺子原来的召回率测不出这个差别)。

召回 92% 但端到端 61%，说明问题在 CoT 或 SQL 生成；两个都低，说明元数据没写好。
**一个总分只能告诉你「不行」，分指标才能告诉你「哪不行」。**

### 判分方式

**不比 SQL 字符串，比执行结果。**同一个问题有无数种正确写法
（JOIN 条件左右互换、列别名不同、子查询 vs JOIN），比字符串没有意义。
比对时只看**值**不看列名，行内值排序、行间集合比对，
这样容忍列别名和排序差异，但抓得住值错、行数错、筛选条件错。

两条从踩坑里学到的规矩：

- **`must_hit_columns` 支持候选组。**同一个问题常有多条正确路径——
  「某天的订单量」既能数 `fact_order.create_time`，也能用
  `dws_shop_daily.stat_date`。只认一条路径，测的就不是系统而是出题人的预设。
- **题目措辞必须让输出列无歧义。**问「客单价最高的10个用户的客单价是多少」，
  模型多返回一列 `user_id` 不能算错。输出不明确的题目没法客观判分。

### 题库构成

50 题，21 类考点：

| 组 | 题号 | 考点 |
|---|---|---|
| A | E01–E22 | 基础覆盖：单表过滤、分组统计、金额字段辨析、枚举值匹配 |
| B | E23–E32 | 跨表多跳：2–3 次 JOIN、层级类目、同名字段消歧 |
| C | E33–E40 | 嵌套聚合：子查询、两个聚合相除、比率计算 |
| D | E41–E45 | 时间窗口：区间、按天分组、上下旬对比 |
| E | E46–E50 | 陷阱题：Schema 根本支撑不了，考的是会不会编 |

陷阱题（手机号、库存、员工数、物流时效、精确年龄）是刻意设计的——
**能诚实说「我没有这个数据」的系统，比什么都敢答的系统可靠得多**，
而这一点不专门测就永远不知道。

### 单次运行有误差，用 --repeat 压掉

同一份代码、同一份题目跑两次，50 题里有 **5 题结果不一样**：

```text
E18  第一次 ✅ → 第二次 ❌        E28  第一次 ❌ → 第二次 ✅
E24  第一次 ✅ → 第二次 ❌        E39  第一次 ❌ → 第二次 ✅
E38  第一次 ✅ → 第二次 ❌
```

源头是关键词抽取本身非确定：模型这次吐「直播间」、下次吐「渠道」，
一路级联到召回、精排和最终 SQL。单次运行因此带着约 ±5% 的误差棒。

**这意味着单次跑出来的前后对比基本是在噪声里找信号。**

```bash
python -m eval.runner --repeat 3
```

重复模式下：

- 每题按**多数**判定通过，展示 `2/3`、`0/3` 这样的通过次数
- 输出单次运行分布和波动幅度：`40/50　38/50　41/50　→　76% ~ 82%，波动 3 题`
- 单列**抖动题**（同一份代码结果不一致的那些）

抖动题本身就是脆弱信号：它说明这道题的链路某一环依赖了模型的随机输出，
比稳定失败的题更值得先看——稳定失败是能力问题，抖动是鲁棒性问题。

### 熔断：宁可没有数字，也不要假数字

一次 150 运行的评测跑到一半断网，后面 26 题全部 0.0 秒失败，重试机制空转 162 次，
最后仍然吐出一份**格式完整的报告**：

```text
端到端准确率     21/50    42%
陷阱题诚实率      0/5      0%
单次运行分布　21/50　21/50　21/50　→　42% ~ 42%，波动 0 题
```

每个数字都是假的。那句"波动 0 题"看着像好消息，其实是故障的指纹——
真正的随机抖动不可能三次完全一致。

如果不逐题去看耗时，很容易把 42% 当成真实退步，然后去修一个根本不存在的问题。
**一个会输出无效数字的评测器，比没有评测器更危险。**

现在评测器会：

1. **区分故障类型。**DNS 失败、Key 失效、余额耗尽属于持续性故障，**不重试**——
   重试一百次也是一样的结果，只会白烧时间掩盖问题。超时、限流才值得重试。
2. **连续 3 次基础设施故障就中止**（`--abort-after` 可调），退出码 2。
3. **中止时一个百分比都不输出。**半截数据算出来的准确率没有意义，
   而一旦印成百分数就会被当成结论。

```text
⛔ 评测未完成，不输出指标
  中止原因　连续 3 次基础设施故障
  故障类型　persistent
  完成进度　23/50 题

  半截数据算出来的准确率没有意义，因此这里不给任何百分比。
  请先排查环境（网络 / DNS / API Key / 余额 / 限流），再重跑。
```

注意 SQL 报错、结果不符这类**系统真实失败**不计入熔断计数，只有环境故障才算。

## 拒答必须建立在完整信息上

陷阱题诚实率这个指标，一度经历了"假 100% → 真 60% → 78% 但误伤 → 100% 且准确率同涨"的曲折。
过程比结论更值得记：

**第一步，发现尺子是坏的。**判分逻辑原本是"CoT 文本出现『缺失』二字就算通过"。
收紧成"给出数字即判编造"之后，真实成绩是 3/15——系统一直在编，
只是判分接受了"嘴上承认、手上照编"。最离谱的一例：

```sql
-- 问"每家店铺有多少名员工"，库里根本没有员工数据
SELECT shop_name, COUNT(*) AS employee_count FROM dim_shop GROUP BY shop_name
-- 每家店恒为 1，标上 employee_count 就交了
```

**第二步，修过头了。**在 CoT Prompt 里写下"宁可回答缺失，也不要给出口径不符的数字"，
再加上结构化阻断（CoT 判缺失就不生成 SQL）。陷阱题 15/15，但**误伤了 5 道正常题**，
端到端从 82% 掉到 78%。

原因在 CoT 的实际输出里：

```text
Q: 北京用户一共下了多少笔订单
数据库: 缺失
处理对象: 缺少 dim_user 的城市字段（如 city/province）用于筛选"北京"用户
```

`dim_user.city` **明明存在**，只是这一轮没被检索召回。
那句"宁可回答缺失"让模型把**"我没看到"**和**"库里没有"**混为一谈。

**第三步，找到真正的变量。**问题从来不在诚实和准确之间取舍，
而在于**做判断时有没有完整信息**。所以：拒答之前，用全量 Schema 复核一次。

```python
if any(_is_missing_schema_step(step) for step in cot_result.steps):
    full_graph = self._build_full_schema_graph()   # 全部 81 个字段
    retry = self.cot_planner.plan(contextual_query, full_graph)

    if not any(_is_missing_schema_step(s) for s in retry.steps):
        emit(Codes.SCHEMA_RECALL_MISS, "实为检索漏召回，已用全量 Schema 重规划")
        cot_result = retry
```

81 个字段放进 Prompt 完全放得下，只在判缺失时多花一次调用。
**一个拒答如果建立在残缺信息上，就没有任何可信度。**

### 结果：两个指标同时到最好

| 指标 | 基线 | 只加诚实约束 | 加全量复核 |
|---|---|---|---|
| Schema 召回率 | 94% | 93% | **99%** |
| 执行准确率 | 82% | 87% | **91%** |
| 陷阱题诚实率 | 80% | 100% | **100%** |
| 端到端 | 82% | 78% | **90%** |

这张表里的 Schema 召回率是**复核后**口径，兜底兜掉多少当时测不出来——
补测见[99% 里有 6 个点是兜底撑的](#回头补测-ecommerce99-里有-6-个点是兜底撑的)。

端到端 82% → 90%，跳出了基线 78~84% 的误差带。
顺带修好了两道**原本稳定失败**的题（E07、E30）——
它们的根因也不是能力不足，是信息不够。

### 把 bug 变成了探针

两个降级码讲出了完整的故事：

```text
SCHEMA_INSUFFICIENT    18 题次    复核后确认缺失，正确阻断
SCHEMA_RECALL_MISS     13 题次    复核后发现能答，检索确实漏了
```

`SCHEMA_RECALL_MISS` 那 13 次是以前根本测不出来的数据。
模型的"缺失"声明成了一个精确的召回失败探针——比任何启发式都准，
因为它是模型自己在说"我需要城市字段但没看到"。

## Chinook：换一个不是我设计的库

前面所有数字都建立在一个闭环上——数据集是我造的，50 道题是我出的，元数据也是我写的。
「元数据质量决定召回准确率」这个结论，在自己搭的场子里当然成立。

[Chinook](https://github.com/lerocha/chinook-database) 是公开的音乐商店示例库，
11 张表 64 个字段，英文命名。它自带的歧义比我刻意埋的还狠：

| 歧义 | 情况 |
|---|---|
| `Name` | 出现在 **5 张表**：`Artist` `Genre` `MediaType` `Playlist` `Track` |
| Customer / Employee | 共享 **11 个同名字段**：`City` `Country` `Email` `Phone` `FirstName`… |
| `Title` | `Album.Title` 是专辑名，`Employee.Title` 是职位 |
| `UnitPrice` | `Track` 里是目录标价，`InvoiceLine` 里是成交快照 |

**这些歧义不是我埋的**——这正是它作为验证集的价值。题库 15 题
（[cases_chinook.py](eval/cases_chinook.py)），中文提问、英文 Schema，含 2 道陷阱题，
难度组合就是真实场景：国内团队用英文命名的库，业务同学用中文提问。

```bash
curl -L -o runtime_data/chinook.db \
  https://github.com/lerocha/chinook-database/raw/master/ChinookDatabase/DataSources/Chinook_Sqlite.sqlite

python -m eval.runner --dataset chinook --repeat 3
```

### 元数据消融：把元数据整份拔掉

Chinook 还能测第二件事，而且能测干净：同一个库、同一套题、同一份代码，
**唯一的变量是业务元数据的有无**。

```bash
python -m eval.runner --dataset chinook --meta ab --repeat 3
```

`--meta none` 把手写的表描述、字段别名、近义字段辨析全部丢掉，只留库里自带的
字段名、类型和样例值；`--meta ab` 两组都跑并输出差值。两组**逐题交错跑**，
不是一组跑完再跑另一组——否则接口在中途变慢或变笨，差值里就混进了时间因素。

写元数据时守的纪律是**只描述 Schema，不看题库**：
每句话都必须是"一个刚接手这个库的数据同学照着表结构和样例值就该写下来的话"。
歧义辨析来自上面那张表，不来自题目——否则元数据就成了答案抄写，差值也就没有意义。

15 题 × 3 次 × 2 组 = 90 次运行：

| 指标 | 无元数据 | 有元数据 | 变化 |
|---|---|---|---|
| **首轮检索召回率** | 9/18　50% | 17/18　94% | **+44pt** |
| **复核救回次数** | 21/45 次 | 3/45 次 | **−18 次** |
| **平均每次耗时** | 8.5s | 6.6s | **−22%** |
| Schema 召回率（含兜底） | 18/18　100% | 18/18　100% | 持平 |
| 执行准确率 | 13/13　100% | 13/13　100% | 持平 |
| 陷阱题诚实率 | 2/2　100% | 2/2　100% | 持平 |
| 端到端准确率 | 15/15　100% | 15/15　100% | 持平 |

差别集中在 6 道题上。无元数据时它们**每次**都要靠全量 Schema 复核救回，
有元数据后一次都不用救：

```text
C02  所有发票的金额合计        首轮漏召回 Invoice.Total
C06  每个流派各有多少曲目      首轮漏召回 Genre.Name、Track.GenreId
C08  Rock 流派总时长          首轮漏召回 Genre.Name
C09  开票金额最高的三个国家    首轮漏召回 Invoice.Total
C11  消费总额最高的客户        首轮漏召回 Customer.FirstName、Invoice.Total
C12  平均每张发票几个明细行    首轮漏召回 InvoiceLine.InvoiceId
```

### 端到端持平，不等于元数据没用

**天花板在加元数据之前就顶住了**，顶住它的是[全量 Schema 复核](#拒答必须建立在完整信息上)。
Chinook 只有 64 个字段，全量 Schema 塞得进 Prompt，所以每一次漏召回都能被捞回来——
无元数据组 45 次运行里有 **21 次（47%）** 是这么救回来的。

代价记在耗时上：两组总耗时差 86.3s，正好省掉 18 次复核，摊下来 **4.8s 一次**，
就是一轮 CoT 规划的往返时间。这个提速和机制对得上，不是接口抖动。

所以这份 A/B 能说的是：**元数据把检索从「一半靠兜底」变成「一次到位」**。
至于它能不能救准确率，这套 15 题验证不了——后来在 ecommerce 上补了一组，
答案是能、值 8 个点，但机制和我当时猜的不一样：
见[真正的变量不是 Schema 大小，是题目难度](#真正的变量不是-schema-大小是题目难度)。

### 先得修尺子：原来的召回率测不出这个差别

第一次跑完 A/B，四个指标**全部持平 100%**，结论看起来是"元数据毫无作用"。

问题出在 `Schema 召回率` 算的是 `schema_context`——那是**复核之后**的 Schema。
一旦触发复核，它就被换成了全库 64 个字段，拿它算召回率等于在问
"全量 Schema 里有没有这个字段"，答案恒为 100%。

真相当时只藏在降级记录里：`SCHEMA_RECALL_MISS` 一组 21 题次、另一组 3 题次。

修法是给 `PipelineResult` 加一份 `retrieval_context`，存**首轮检索**的结果，
在复核改写 `schema_graph` 之前就留好；评测器据此新增两个指标：

| 指标 | 衡量什么 |
|---|---|
| 首轮检索召回率 | 检索这一轮就召回了，没靠兜底 |
| 复核救回次数 | 首轮漏召回、靠全量 Schema 重规划补上的运行数 |

**一个测不出变化的指标，和一个输出假数字的评测器是同一种病。**

新指标加完，第一件事是回头把 ecommerce 那 50 题重测一遍——那里记着的
"Schema 召回率 99%"是同一个复核后口径。

### 回头补测 ecommerce：99% 里有 6 个点是兜底撑的

50 题 × 3 次 = 150 次运行，跑的是当前出厂配置：

| 指标 | 重测 | [上面那张表](#结果两个指标同时到最好)记的 |
|---|---|---|
| **首轮检索召回率** | **62/67　93%** | 当时测不出来 |
| Schema 召回率（含兜底） | 66/67　99% | 99% |
| **复核救回** | **13/150 次运行　8.7%** | — |
| 执行准确率 | 41/45　91% | 91% |
| 陷阱题诚实率 | 5/5　100% | 100% |
| 端到端准确率 | 46/50　92% | 90% |

三项分毫不差，端到端 92% 落在原记的 86%~94% 误差带内——**那张表没问题，只是少了一行**。
真实的首轮召回是 93%，兜底兜掉 6 个点：67 个必中字段里的 4 个、150 次运行里的 13 次。

> 本节与下一节的数字测于[强命中补回收紧](#追查-e24同义近邻让压倒性命中判据失效)**之前**。
> 收紧之后同配置重测：首轮召回 94%（+1 个字段）、复核救回 11/150、端到端 90%，
> 各项都落在误差带内，但严格说来不再逐字对应当前代码。

漏召回的两处都在近义字段密集的地方：E19 漏 `fact_user_behavior.behavior_type`，
E27 漏 `fact_refund.refund_amount`。

### 在 ecommerce 上再做一次：元数据值 8 个点

Chinook 那组的结论停在"元数据买到的是检索，不是准确率"。但那是 64 个字段、
15 道相对直白的题。换到 81 个字段、50 道含嵌套聚合和比率的题上，同一个开关再拉一次
（50 题 × 3 次 × 2 组 = 300 次运行）：

| 指标 | 无元数据 | 有元数据 | 变化 |
|---|---|---|---|
| **首轮检索召回率** | 55/67　82% | 62/67　93% | **+10pt** |
| Schema 召回率（含兜底） | 63/67　94% | 66/67　99% | +4pt |
| 执行准确率 | 36/45　80% | 40/45　89% | **+9pt** |
| **端到端准确率** | **41/50　82%** | **45/50　90%** | **+8pt** |
| 陷阱题诚实率 | 5/5　100% | 5/5　100% | 持平 |
| 复核救回 | 25/150 次 | 15/150 次 | −10 次 |

两组的单次分布分别是 80%~82% 和 88%~90%，各自波动 1 题——**8 个点远在误差带之外**。

无元数据时漏召回的字段，全部落在[刻意埋的纯业务口径词](#刻意埋的坑)上：
`avg_order_amount`（客单价）、`freight_amount`（运费）、`discount_amount`（优惠）、
`item_amount`（成交金额）、`gmv`（销售额）、`stay_seconds`（停留时长）——
业务怎么说、字段怎么写，字面零重合。这正是当初设计这套 Schema 想考的东西。

**但不是单向变好**：翻正 7 题（E05 E07 E33 E38 E39 E42 E43），翻负 3 题（E23 E36 E37），
首轮召回另有 4 题变差——其中 E24「北京用户一共下了多少笔订单」，就是上面那个
经典漏召回案例，加了元数据反而从 1/1 掉到 0/1。净值是正的，
但**元数据不是无条件的改进**。

### 真正的变量不是 Schema 大小，是题目难度

|  | 无元数据 | 有元数据 |
|---|---|---|
| **ecommerce**　81 字段 · 50 题 | 首轮 82%　端到端 **82%** | 首轮 93%　端到端 **90%** |
| **Chinook**　64 字段 · 15 题 | 首轮 50%　端到端 **100%** | 首轮 94%　端到端 **100%** |

上面写过一个推论：*换一个字段多到塞不进 Prompt 的库，兜底不成立，
召回差距就会变成准确率差距*。**这个机制说错了**——81 个字段照样塞得进 Prompt，
兜底照样在跑（25 次），端到端还是掉了 8 个点。

真正的变量是题目难度。Chinook 无元数据的首轮召回只有 50%，比 ecommerce 无元数据的
82% 还差得多，端到端却稳在 100%：那 15 道题只要字段到齐就能答对，兜底把字段补齐就够了。
ecommerce 有嵌套聚合、比率、区间对比，**兜底能补上字段，补不了生成**——
E23、E36 两题元数据反而把首轮召回从 2/3 提到 3/3，端到端却翻负了。

所以完整的说法是：**元数据的收益先落在检索上（+10pt ~ +44pt），
能不能传导到准确率，取决于题目在字段到齐之后还剩多少难度。**

### 这个结论的边界

- **15 题、两组都 100%**，说明这套题对当前链路偏容易，测不出生成环节的任何差别。
- **C10「2023年一共开了多少张发票」两组都漏**：`Invoice.InvoiceDate` 首轮都没召回，
  每次都靠复核救回。给它写了别名和 `keyword_text` 也没用，这是元数据没吃下的一块。
- 有元数据组多出 6 次 `DOMINANT_KEYWORD_RESCUED`（字面命中压倒性的字段被精排淘汰又强制补回），
  说明精排阈值对高质量元数据偏保守了。**这条线索后来查下去了，见下一节。**

### 追查 E24：同义近邻让"压倒性命中"判据失效

上面那组 A/B 里有一处反常：**E24「北京用户一共下了多少笔订单」加了元数据反而漏召回**，
首轮从 1/1 掉到 0/1。它正是[全量复核那一节](#拒答必须建立在完整信息上)的原始案例，
值得查到底。

逐层拆开之后，元数据其实是有效的——**问题出在下游**。

**BM25 层：元数据把同名字段分开了**

```text
无元数据  『北京用户』:  user_name 22.12 │ dim_shop.city 10.55 │ dim_user.city 10.55 │ province 9.33
有元数据  『北京用户』:  dim_user.city 17.52 │ province 16.08 │ dim_shop.city 10.11 │ user_name 8.70
```

注意无元数据那行：`dim_shop.city` 与 `dim_user.city` **同为 10.55 分**——
两个字段的索引文本几乎等价，BM25 根本分不开。加元数据后 `dim_user.city` 升到第一，
消歧成功了。

**精排层：全部名额押给了 dws 汇总层**

另一个关键词『订单笔数』在有元数据时强命中 `dws_user_summary.total_order_count`
（"用户累计下单笔数"）。精排是**逐字段**打分的，它不知道"这组字段合起来能不能回答问题"，
于是 12 个名额全给了 dws 汇总层——而那张表没有城市维度，答不了"北京"这个筛选条件。
`dim_user` **整张表**被挤出了 SchemaGraph。

对比两组的精排分数，能看出元数据干了什么：

```text
无元数据  0.0015 / 0.0008 / 0.0007 …   ← 索引文本稀疏，精排无法区分，近似透传 RRF 顺序
有元数据  0.8002 / 0.7558 / 0.7140 …   ← 排序"确信"，于是确信地押错了
```

`dim_user.city` 在无元数据组活到第 5 位是**运气**，不是判断。

**强命中补回为什么没接住**

那个机制的判据是"甩开第二名 3 倍"。但 `dim_user.city` 17.52 vs `dim_user.province` 16.08，
比值 1.09——**第二名往往是第一名的同义近邻**，索引文本高度重合，分数天然咬得死紧，
谁也甩不开谁。无元数据时更极端：`dim_user.city` 与 `dim_shop.city` 同分，比值正好 1.00。

所以补了两条判据：分数达到 `min_score` 的 2 倍算强命中，不要求断层；
并列的近邻（0.85 倍以内）一起补回，分不清"北京"指 city 还是 province 就两个都给。

### 收紧：一个机制该不该留，看它的代价

第一版放开了写，**首轮召回上去了，稳定性掉下来了**：

| 指标 | 改前基线 | 放开版 | **收紧版** |
|---|---|---|---|
| 首轮检索召回率 | 93%　62/67 | **99%　66/67** | 94%　63/67 |
| 复核救回 | 13/150 | **3/150** | 11/150 |
| 补回触发 | 3 题次 | 34 题次 | 11 题次 |
| 执行准确率 | 91% | 87% | 89% |
| 端到端准确率 | 92% | 88% | 90% |
| 抖动题 | 7 道 | 12 道 | 9 道 |
| **单次分布波动** | **1 题** | **7 题** | **1 题** |

放开版触发了 34 次，等于每 4~5 次运行就往 SchemaGraph 里硬塞最多 4 个字段。
端到端 88% 单看还在误差带里，但**误差带本身变宽了**——三次分别是 47/50、40/50、45/50。
按[抖动是脆弱信号](#单次运行有误差用---repeat-压掉)那套判据，这是回归，不是改进。

收紧的办法是给强命中判据加一个前提：**该字段所属的表整张都不在命中集里**。
E24 的真实病灶是 `dim_user` 整张表消失、连 JOIN 都做不了；
而那 34 次里有三分之二是往已经在图里的表上再塞字段，纯噪声。

收紧后稳定性完全回到基线（波动 1 题、端到端 90%），触发降到 11 次。

**但收益也跟着缩了**：首轮召回只剩 94%，比基线高 **1 个字段**（62/67 → 63/67）。
Chinook 侧三版没有任何差别，都是首轮 94%、端到端 15/15。

所以如实记下来：**这个机制修的是一个已定位的真实缺陷，但在现有两套题上，
净收益约等于 1 个字段，代价为零。** 留着它是因为缺陷本身成立——换一个同名字段
更密集的库，同义近邻互相压制会比这里更常见——而不是因为它在这两套题上测出了什么。

## 结果校验与回调修正 · 自洽性投票

原作者在 README 里标注「暂不包含结果校验与回调修正」，这是补上的那一块。
两个机制都可配置，**但都不该记在"准确率提升"账上**，原因见下。

```python
PipelineConfig(
    sql_repair_attempts=1,      # SQL 执行失败时把报错喂回模型重生成
    self_consistency_runs=1,    # 1 = 关闭；N = 跑 N 次按执行结果取多数
)
```

评测器也带上了对应开关：

```bash
python -m eval.runner --repeat 3 --self-consistency 3 --repair 1
```

### 回调修正：功能补上了，但当前无事可做

执行器的报错是一手信息——`no such column: fact_order.category_id`
直接点名了问题所在，比让模型凭空重想一遍有效得多。

但实测 `SQL_REPAIRED` 一次都没触发。最近一轮全量评测的失败构成是
「结果不符 5 题」，**零个 SQL 报错**——早先那些 `no such table`、
`no such column` 在前几轮已经被修掉了（库名前缀剥除、全量 Schema 复核）。

**它现在是保险不是修复**，换新库、换模型时才会派上用场。

### 自洽性投票：数学上有前提，当前净效果为零

先说为什么需要它。裸调 API，同一个 prompt、`temperature=0`，
DeepSeek 4 次给出 **4 种不同输出**，thinking 开关无关：

```text
1. 数据库索引是一种以额外存储和写入开销为代价、通过预排序的数据结构（如B+树）将查询…
2. 数据库索引是一种以额外存储和写入开销为代价、通过预排序的数据结构（如B+树或哈希表）…
3. 数据库索引是一种以额外存储和写入开销为代价、通过预排序的数据结构（如B+树）加速…
4. …
```

这不是本项目的 bug，是 LLM 推理服务的固有性质：
`temperature=0` 只保证贪心解码，不保证跨请求确定性。

**但多数投票只在单次正确率 > 50% 时才有增益**，低于 50% 时它会放大错误答案。
6 道嵌套聚合题的 A/B 对比逐题验证了这一点：

| 题 | 单次正确率 | 投票关闭 | 投票 3 次 |
|---|---|---|---|
| E33 / E34 / E40 | ~100% | 3/3 | 3/3 |
| E35 | ~67% | 2/3 | **3/3** ↑ |
| E37 | ~33% | 1/3 | **0/3** ↓ |
| E36 | ~0% | 0/3 | 1/3 |
| **总计** | | **4/6** | **4/6** |

推上去一道，压下去一道，**净效果精确为零，成本却是 2.7 倍**
（每题 12s → 32s）。所以默认关闭。

它在两种情况下值得开：模型换成更强的（单次正确率整体上移过 50%），
或者对"错了代价很大"的问题单独开启，用成本换确定性。

`SELF_CONSISTENCY_DISAGREEMENT` 这个降级码本身有价值——
它精确标出了哪些问题模型自己都拿不准。

## Web 界面

```bash
python -m askdata_web.server
# 打开 http://127.0.0.1:8000
```

用标准库的 `http.server`，**不引 Flask/FastAPI**——整个项目的核心链路
只依赖 numpy 加标准库，这一层没理由破坏这个性质。

```bash
python -m askdata_web.server --port 8080 --dataset trade
```

### 它展示什么

界面不是一个"输入问题、返回表格"的黑盒，而是把**链路的每一步中间产物**摊开：

```text
路由        database_query / data_qa，以及判定理由
01 关键词    抽取结果；发生指代消解时额外显示改写后的问题
02 Schema   命中的表与字段，字段悬停显示业务含义，附表关联关系
03 CoT      四元组规划原文
04 SQL      生成的语句
05 结果     执行结果表格
降级        本次运行的降级记录，没有就显示"无降级"
```

这条链路本身才是项目的内容，藏起来就只剩一个普通的查询框了。

### 顶栏的三个状态

```text
ecommerce · 11 表 · 81 字段     数据集规模
deepseek · deepseek-flash       当前供应商，未配置 Key 时显示 Mock 并标红
本地向量与精排 已启用             未启用时标红
```

**配置降级在界面上一眼可见**，不用去翻日志才发现自己看的是 Mock 结果。

### 多轮追问

会话记忆默认开启，可以直接追问：

```text
第一问：销售额最高的三个店铺，店铺名称和销售额分别是多少
第二问：它们的退款金额分别是多少
        → 界面显示：指代消解 → 销售额最高的三个店铺（臻品自营店15、
          优选旗舰店1、旗舰旗舰店7）的退款金额分别是多少
```

「新会话」按钮换一个 session_id，不删除旧记忆——短期记忆本身是审计痕迹。

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 供应商、数据集规模、降级状态 |
| POST | `/api/ask` | `{query, session_id}` → 整条链路的中间产物 |
| POST | `/api/reset` | 返回一个新的 `session_id` |

同一时刻只服务一个请求（整条链路是同步的），避免并发把会话记忆搅乱。
异常如实返回给前端，不静默吞掉。

## Schema 索引接进主链路

原本 `schema_indexing` 建好 Milvus 三级索引，主链路却每次启动重扫源库——
**模块从没被接进来过**。现在补上了：

```python
HybridSchemaRetrievalService.from_milvus(
    uri="runtime_data/schema_index.db",
    embedding_client=..., rerank_client=...,
)
```

### 先说清楚：当前规模下没有性能收益

动手前先量了一遍启动耗时，结果推翻了我原本的理由：

```text
建库 + 扫 Schema + 编码      0.36s     ← 我以为的瓶颈
载入两个 bge 模型            14.98s    ← 真正的瓶颈（98%）
```

索引能省的只有那 0.36 秒，而查询时还要用 bge 编码 query、用 reranker 精排，
**模型必须加载，一秒都省不掉**。

它的价值在别处：**规模**（81 个字段编码 0.33 秒，8100 个就是 33 秒）、
**解耦**（换库加库不用重扫）、**共享**（多个查询进程共用一份索引，而不是各建各的）。
这些在 Demo 规模上都体现不出来。

### 接的过程挖出三层问题

**一、索引不是自包含的。**只存了 9 个标量字段，而 `ColumnSchema` 有 17 个。
缺的正是 `description`、`aliases`、`samples`、`business_usage`、`value_range`——
**恰恰是渲染进 CoT 和 SQL 提示词的业务语义**。照现状接进去，链路照样能跑，
提示词却悄悄退化成只剩字段名和类型。修法是把完整的 `ColumnSchema` 与 `TableSchema`
序列化成 JSON 一并存入。

**二、两个模块各有一份 `TableRelation`。**字段完全相同，但只有 `schema_indexing`
那份带 `join_condition` 和 `relation_key` 两个 property——**字段一样、行为不一样，
类型看着兼容，一调就炸**。改成鸭子类型取值，取不到就按关联键现拼。

**三、两个模块各实现了一套三级索引文本构建。**产出的文本 **81 个字段全都不一样**。
这条最要命：光接上不校验的话，检索结果会悄悄漂移。

第三条也决定了架构上谁是权威——**检索服务那一套**，因为只有它会读取
`business_meta` 里手写的 21 条 `keyword_text` 和 15 条 `rerank_text`，
而那些手写文本是这个项目最值钱的资产。所以索引的职责是
**持久化检索服务的产出**，而不是自己再造一遍：

```python
builder.build(columns=..., relations=..., tables=..., documents=service.documents)
```

### 验证：不是"能加载"，而是"加载出来一模一样"

```text
keyword_text   不一致 0 个
vector_text    不一致 0 个
rerank_text    不一致 0 个
向量最大差异    0.00e+00

4/4 条查询的提示词上下文逐字节一致
```

这条断言写进了 [tests/test_diagnostics.py](tests/test_diagnostics.py)
的 `SchemaIndexRoundTripTestCase`。只断言"能加载"是不够的——
**加载成功但内容退化，正是这个项目反复踩的那类静默失败。**
