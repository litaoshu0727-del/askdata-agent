[![tests](https://github.com/litaoshu0727-del/askdata-agent/actions/workflows/tests.yml/badge.svg)](https://github.com/litaoshu0727-del/askdata-agent/actions/workflows/tests.yml)

自然语言问题 → Schema 检索 → CoT 规划 → SQL 生成 → 执行，一条可评测、出错会告警的
Text2SQL 链路。

陷阱题（库里根本没有这个数据）诚实率在所有题库上都是 100%。留出集由全新上下文的子代理
盲写，在第一次运行之前冻结提交（[协议](docs/实验记录.md#协议)）。留出集五 150 次运行错 1 次，
和第四套封存时的版本分不出差别。留出集六换了更难的出题规范（业务说法、不点字段，多表连接、
两层聚合、窗口排名、相对时间、否定集合），失败几乎全在 SQL 生成。照着它加的每组前 N 规则和修正
报错分析，在同一份规范新写的留出集七上测出了收益：12 道题变好、0 道变差（p≈0.03），每组前 N
被丢掉 6 → 0；之后加的修正最多 2 次、结果形状检查在这套题上测不出效果。留出集八允许题面靠口径约定、不写订单状态，
13 道这样的题 29 → 35 / 39 次；基线已经 27/30、20/20，版本之间的差别都不显著。当前版本 150 次运行错 5 次。
留出集九换了一个没参与设计的库 Sakila（元数据在出题之前写好）：109/120 次，比留出集八低 6 个百分点左右；
拿掉元数据或 SQL 规则，端到端都没有测出差别——元数据让首轮召回 87% → 98%，规则让执行报错 24 → 4 次，
剩下的失败都是已知的 SQL 结构错误。照着这些错加了三项结果检查（分组粒度、窗口的上一期、每组前 N），留出集十三个库
一起验：触发 5 次、原 SQL 都是错的、改对 4 次，但总分 200 / 199 / 210 分不出差别——同一份规范写的题已经接近饱和。

**[大库压力测试](docs/实验记录.md#大库压力测试1076-个字段)**：电商 11 张表加 12 个干扰业务域，88 张表 1076 个字段，
全量 Schema 14.8 万字。121 道电商题（主题库加留出集三、四）端到端 120/121，与小库持平，平均耗时
11.9s 对 11.2s；没见过的留出集五 30 题 90/90 次运行，也和小库相同。

## 主要结论

1. **拒答要建立在完整信息上。**模型常把"我没看到这个字段"说成"库里没有"。拒答前用全量
   Schema 复核一次，端到端 82% → 90%，诚实率 80% → 100%
   （[详情](docs/实验记录.md#拒答必须建立在完整信息上)）
2. **元数据的收益先落在检索上。**Chinook 首轮召回 50% → 94%，ecommerce 端到端 +8 个点；
   能不能传导到准确率，取决于字段到齐之后题目还剩多少难度
   （[详情](docs/实验记录.md#真正的变量不是-schema-大小是题目难度)）
3. **手写的精排文本比自动生成的还差。**删掉之后，Chinook 留出集首轮召回 88% → 98%，
   ecommerce 留出集 6 道题变好、0 道变差
   （[详情](docs/实验记录.md#第二套留出集修-chinook-精排在没见过的题上验证)）
4. **分数涨了，先问是系统变了还是判分变了。**主题库 87% → 98% 的 11 个点里，大约一半是
   判分校正（[详情](docs/实验记录.md#这条线的账)）
5. **最危险的是零告警的错答案。**链路跑通、数字看着合理，中间某一环已经悄悄失效。
   降级告警和筛选值守卫都是为它做的（[详情](docs/实验记录.md#堵住零告警筛选值守卫)）
6. **两个机制做了但没有收益。**自洽性投票净效果为零、成本 2.7 倍，默认关闭；
   Schema 索引在当前规模下省不了时间，启动耗时的 98% 在加载模型
   （[投票](docs/实验记录.md#自洽性投票数学上有前提当前净效果为零)、
   [索引](docs/实验记录.md#先说清楚当前规模下没有性能收益)）

## 链路

```text
用户问题
  → 路由：要查新数据走 Text2SQL；结果解释、指标口径、历史追问走 data_qa，不查库
  → 指代消解（多轮追问时，"它们"改写成上一轮的具体对象）
  → 关键词抽取
  → Schema 混合检索：BM25 + 向量 → RRF（按关键词保底进池）→ 精排 → 关键词覆盖 → 时间约束保底
  → SchemaGraph（关键词落在的表之间不连通时，沿外键补桥接表）
  → CoT 四元组规划 ── 判"缺失"时用全量 Schema 复核一次
  → SQL 生成 → 执行 ── 报错时带报错回调修正
  → 筛选值守卫：问题提到的枚举取值 SQL 没用上，就带提示重规划
  → 结果 + 降级记录
```

| 目录 | 内容 |
|---|---|
| `schema_indexing/` | Schema 索引构建（离线） |
| `schema_retrieval/` | 混合检索、精排、SchemaGraph |
| `cot_planning/` | CoT 四元组规划 |
| `sql_generation/` | SQL 生成与修正 |
| `mcp_router/` | 路由与 SQLite 执行 |
| `askdata_pipeline/` | 端到端编排、路由、指代消解、筛选值守卫、数据集 |
| `askdata_memory/` | 长短期记忆（[说明](askdata_memory/README.md)） |
| `askdata_web/` | Web 界面 |
| `eval/` | 评测器与题库 |

相对基线的新增：DeepSeek 接入与本地 bge 向量 / 精排、电商与 Chinook 两个数据集、
指代消解、全量复核、筛选值守卫、时间约束保底、SQL 回调修正与自洽性投票、降级告警、
Web 界面、评测器与三套留出集。

## 快速开始

```bash
conda create -n askdata python=3.12 && conda activate askdata
pip install -r requirements.txt
cp .env.example .env        # 填上 DEEPSEEK_API_KEY；本地向量与精排默认已开启
```

```bash
python -m askdata_pipeline.ecommerce_demo --query "客单价最高的10个用户是谁"
python -m askdata_pipeline.multi_turn_demo      # 五轮追问
python -m askdata_web.server                    # http://127.0.0.1:8000
```

模型分工：关键词抽取、CoT 规划、SQL 生成走 DeepSeek；向量和精排走本地
`bge-small-zh-v1.5` / `bge-reranker-base`（首次运行自动下载，约 1.2GB）。也支持阿里云百炼，
配置项见 [.env.example](.env.example) 和 [llm_config.py](llm_config.py)。不配任何 Key
时全部走 Mock，能跑通，但结果没有意义，降级记录里会写明。

## Web 工作台

```bash
conda activate askdata-repro
python -m askdata_web.server --dataset ecommerce --port 8000
# 浏览器打开 http://127.0.0.1:8000

# 手机也要打开：监听所有网卡，启动时会打印手机用的局域网地址
python -m askdata_web.server --dataset ecommerce --host 0.0.0.0 --port 8000
# 同一网络里谁都能连上并消耗你的模型额度；校园网、公司网常隔离设备，手机可能仍连不上
```

界面直接使用现有 Python 服务，不需要 Node.js、npm 或前端构建步骤：

- 对话式布局：左侧按会话列出历史（最近 20 个，每个最多 30 轮，存在当前标签页的 sessionStorage），
  新建会话（⌘K）会换一个后端 session_id；点开旧会话可以接着追问，追问和指代消解都在同一条对话流里。
- 每一轮先把链路摊开成可展开的步骤行——改写问题、检索 Schema、规划查询、执行 SQL、降级记录，
  展开能看到关键词、按四元组排好的规划（接口的 `plan` 字段）、带高亮的 SQL 和返回行数。
  下面是回答和结果：表格 / 柱状图切换、选择数值指标、CSV 导出、复制 SQL。
  接口每步骤最多返回 200 行，导出范围与页面相同，超出会标注；柱状图显示前 15 条非空记录。
- 规划判定库里缺数据而拒答时，回答直接列出缺的是什么（取自规划的处理对象，表名字段名标成代码），
  并给出跳到数据源页查看相关表字段的按钮；欢迎页上那道用来演示拒答的示例题会标注出来。
  其他原因没生成 SQL 时，规划那一行默认展开，直接看到原文。
- 右侧运行详情（概览 / SQL / Schema）对应某一轮：路由、耗时、检索关键词、降级记录、命中的表和关联。
  等待时只显示实际耗时，不模拟逐步进度——接口一次返回整条链路。
- 数据源页从 `GET /api/schema` 获取表、字段、类型与业务说明，支持按业务词搜索元数据，
  不读取业务行、不调用模型。数据集由启动时的 `--dataset` 参数选择。
- 浅色 / 深色跟随系统，右上角可以手动切换；窄屏时侧栏和运行详情收成抽屉。

只验收页面交互时可启动原始交易库的离线 Demo（不读取本机密钥，也不加载本地模型）：

```bash
env -u DEEPSEEK_API_KEY -u DASHSCOPE_API_KEY -u DASHSCOPE_WORKSPACE_ID \
  -u ASKDATA_LOCAL_MODELS ASKDATA_DISABLE_DOTENV=1 \
  python -m askdata_web.server --dataset trade --port 8001
```

打开第一个示例问题“查询总交易笔数大于50000的利率是多少”。Mock 状态会在页面中明确标注；
其他业务问题需要配置真实模型。前端文件在 `askdata_web/static/`。

## 数据集

- **ecommerce**：自建，11 表 81 字段，约 7000 行，固定随机种子。刻意埋了近义字段：9 个
  金额字段、两张表里都有的 `pay_amount` / `city` / `finish_time`、"客单价""销售额"这类
  和字段名字面零重合的业务词
- **ecommerce_big**：压力测试用。电商 11 张表一字不改，再加人力、财务、采购、生产等 12 个相邻
  业务域的干扰表，88 张表 1076 个字段；干扰域避开陷阱题的主题，和电商之间没有外键，元数据薄。
  电商的题在这个库上答案不变（[bigdb_data.py](askdata_pipeline/bigdb_data.py)）
- **Chinook**：公开的音乐商店库，11 表 64 字段，英文命名、中文提问。`Name` 出现在 5 张表，
  客户和员工共享 11 个同名字段——这些歧义不是我埋的
- **Sakila**：MySQL 官方示例库（DVD 租赁连锁），15 表 86 字段，验证泛化用：没有调优用的主题库，题只在
  留出集九里，元数据在出题之前写好。从 jOOQ 的 SQLite 脚本建库，命令见 [sakila_data.py](askdata_pipeline/sakila_data.py)

```bash
curl -L -o runtime_data/chinook.db \
  https://github.com/lerocha/chinook-database/raw/master/ChinookDatabase/DataSources/Chinook_Sqlite.sqlite
```

**换成自己的库**：照着 [ecommerce_data.py](askdata_pipeline/ecommerce_data.py) 写建表语句
（外键一定要声明，表关系靠它提取）、业务元数据（别名和近义字段辨析最值钱）、在
`_prepare_dataset()` 里加一个分支。检索参数默认按大库设置，新库不用调；字段多到全量 Schema
超过 4 万字时，复核自动改用有限扩展（`REVIEW_SCHEMA_BOUNDED` 会写明用了哪一级）。

## 评测

```bash
python -m eval.runner --repeat 3                                # ecommerce 主题库
python -m eval.runner --dataset chinook --repeat 3
python -m eval.runner --dataset ecommerce_big                   # 1076 个字段的压测库
python -m eval.runner --case E36                                # 单题
python -m eval.runner --dataset chinook --meta ab --repeat 3    # 元数据消融
python -m eval.runner --bank holdout3 --repeat 3                # 留出集（已用过会提醒）
python -m eval.rejudge_runs                                     # 判分改了以后重判存下的运行记录（不调模型）
python -m eval.multiturn --dataset chinook --repeat 3           # 多轮追问：一组追问在一个新会话里问，每一轮单独判分
python -m eval.runner --bank probes --tag 探针:一对多 --repeat 3  # 探针：整数相除、一对多连接
python -m eval.probe_regression                                 # 全部探针一键回归，和上一次比
python -m eval.runner --repeat 3 --save-runs runtime_data/runs/main.jsonl   # 保存过程记录
```

- **比执行结果，不比 SQL 字符串**：列名不比、列顺序不限，但列的对应关系对所有行必须是同一套
  （员工和上级的名字逐行对调会判错，[详情](docs/实验记录.md#判分改严列的对应关系对所有行一致)）；行间按集合比对。
  数值比到题面要求的小数位（"保留 N 位小数"，没写就是 2 位），取整规则和 SQLite 的
  `ROUND` 一致
- **多返回的列不算错**（第七套之后）：行数相同，能挑出同一组列和参考答案逐行对上，就算对；报告里
  单独列出这类次数，记录里带 `extra_columns`，严格口径随时能算。问"差几单"时把两段各自的订单数也给出来，
  对用户没有坏处（[详情](docs/实验记录.md#时间差和多返回的列)）
- **探针一键回归**：改了提示词、元数据之后跑 `python -m eval.probe_regression`：全部 147 道探针每题 3 次，
  6 个进程并行，约 14 分钟；按批次汇总，逐题和上一次完整运行比，列出通过率掉一半以上的题。题面或参考答案
  改过的题不比。要调真实模型，CI 里跑不了（[详情](docs/实验记录.md#探针一键回归)）
- **分指标统计**：首轮检索召回、Schema 召回（含兜底）、执行准确率、陷阱题诚实率、端到端，
  分开看才知道错在哪一环
- **`--repeat`**：关键词抽取不确定，单次运行有约 ±5% 波动，按多数判定
- **熔断**：断网、Key 失效、余额耗尽这类故障连续 3 次就中止，而且一个百分比都不输出——
  半截数据算出来的准确率比没有更危险
- **`--save-runs`**：每次运行追加一行 JSON，带提交号、判定、降级详情、CoT 原文、结果样本，
  以及 `sql_trace`——执行过的每一条 SQL，包括守卫重规划前的首轮 SQL、回调修正前报错的 SQL、
  自洽性投票落选的几次。逐行落盘，评测中途熔断也不丢
- 并行跑时每个进程用不同的 `--db-path`，否则几个进程同时重建同一个库会报 disk I/O error

## 降级告警

链路上每一处已知的降级点都有探针，出问题时在 stderr 留一行告警，并通过
`PipelineResult.diagnostics` 带出来。常看的几个：

| Code | 含义 |
|---|---|
| `MODEL_MOCK_FALLBACK` / `EMBEDDING_MOCK_FALLBACK` / `RERANK_MOCK_FALLBACK` | 没配 Key 或本地模型，对应环节走了 Mock |
| `MODEL_CALL_RETRIED` | 模型接口返回 429 / 5xx、超时、或者正文没读完就断了，已退避重试（[llm_http.py](llm_http.py)）；402、401 这类不重试 |
| `SCHEMA_RECALL_CAPPED` | 精排名额相对候选数过小，可能截掉了需要的字段 |
| `SCHEMA_RECALL_MISS` | 首轮检索漏召回，已用全量 Schema 复核救回 |
| `FILTER_VALUE_DROPPED` | 问题提到的枚举取值没出现在 SQL 里，筛选条件疑似被丢 |
| `TIME_FIELD_RESCUED` | 问题有时间约束，检索结果里缺时间字段，已补回 |
| `JOIN_PATH_BRIDGED` | 关键词落在的表之间不连通，已沿外键补上桥接表和关联键 |
| `REVIEW_SCHEMA_BOUNDED` | 全量 Schema 超出长度预算，复核 / 守卫重规划改用有限扩展，或不复核 |
| `EMPTY_RESULT_SET` | SQL 成功但返回 0 行，多轮追问里常见于凭空推断的 ID |
| `RESULT_SHAPE_SUSPECT` | 问题只要一个数，结果却有多行（两层聚合压成了一层），已带提示重新生成一次 |
| `RESULT_GRAIN_SUSPECT` | 分组比题目要的细：数了组合没数对象（问客户数数成了客户×日期），或同一个维度出现好几行，已带提示重新生成一次 |
| `RESULT_WINDOW_SUSPECT` | `LAG` / `LEAD` 和按时间筛选写在同一层，范围内第一期的上一期被筛掉了（结果有空值），已带提示重新生成一次 |
| `RESULT_TOPN_SUSPECT` | 问每组前 N，结果的分组列某个值超过 N 行（组内没截断），已带提示重新生成一次 |
| `RESULT_TRUNCATED` | 结果超过 1 万行，只保留前 1 万行；多半是漏了 `GROUP BY` 或关联条件 |

完整列表见 [askdata_diagnostics.py](askdata_diagnostics.py)。

## 局限与待办

- **大库只测过合成的。**1076 个字段的压测库上端到端与小库持平，复核的有限扩展也接住了漏召回
  （H3E27），但干扰域的元数据薄、和电商之间没有同名实体的真歧义，只问电商的题。真实数仓上还没
  测过，也只在 SQLite 上测过
- **多数改动在陌生题上没有可帮的题**：时间字段只留保底、守卫跳过题目自带口径的取值、候选池按
  关键词保底（第四套），桥接表、复核长度预算、时间保底的两处改动、守卫只查相关表、一对多规则
  （第五套）。两套题里都没有落在它们针对的失败形态上的题，收益未测出，代价也未测出。更难的
  第六套拉开了分数，但三个版本的差别仍在波动范围内
- **更难的题上，错在 SQL 生成**：第六套当前版本错的 8 次里，"每组前 N"被丢掉 3 次、外层引用
  子查询里没输出的列 2 次（修正那一步没救回）、两层聚合压成一层 1 次、多一列或值不对 2 次。
  前两类后来加了规则和修正提示的报错分析，在留出集七上测出了收益（每组前 N 被丢掉 6 → 0）；两层压成
  一层加了结果形状检查，重放 18/21 改对，但留出集七上只触发 1 次，没测出效果。留出集七剩下的失败逐题看过：
  "全都是同一个 X"把 X 放进了分组、退款连到明细被重复累加，各加了规则（退款那条还在业务元数据里写明了"一笔订单
  只属于一个类目"），探针上规则相关的失败 11 → 3；留出集八上这两类基线就没错，没有可帮的题
  （[详情](docs/实验记录.md#全都是同一个-x和挂在订单上的退款)）。"分组比题目要的细"（问客户数却数了客户×日期、
  GROUP BY 里多了没输出的列）规则压不稳，改成生成后检查：离线误报 0，实测触发 14 次改对 12 次，但只抓得住历史
  错误运行的 14%（[详情](docs/实验记录.md#分组比题目要的细生成后检查)）。窗口的上一期被筛掉、每组前 N 没截断也照这个
