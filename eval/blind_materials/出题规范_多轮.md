# 出题规范：多轮追问评测题（三个库）

你要为一个"用中文问数据库"的 Text2SQL 系统写评测题。这一套测的是**多轮追问**：用户在同一个会话里先问一个问题，
再顺着前面的问题和答案接着问。系统记得这个会话里之前的问答；每一轮它都要自己弄清楚这一句问的是什么，
找出相关的表和字段、写 SQL、执行、返回结果。

评测时，一组追问在一个新会话里按顺序依次问。**每一轮单独判分**：把系统这一轮返回的结果，和你为这一轮写的
参考 SQL 的执行结果比对。

## 能用的材料（只用这些）

- `ecommerce.md`、`chinook.md`、`sakila.md`：三个库的建表语句和数据字典（表描述、字段描述）。sakila 是一家
  DVD 租赁连锁店的库；数据字典里写明了没有数据的列，不要拿来出普通题
- `ecommerce.db`、`chinook.db`、`sakila.db`：三个 SQLite 库本身，可以随意查询，用来探数据、验证参考 SQL
- `evalcase.py`：题目的数据结构

## 不要做的事

- 不读本目录以外的任何项目文件：包括 README、docs/、eval/ 下的已有题目、git 历史
- 不运行被测系统，也不读它的代码
- 如果你的会话环境里自动带了项目信息（例如 git 状态、提交标题），不要据此出题，并在最后的报告里如实说明看到了什么
- 有任何例外（比如不小心看到了什么），如实报告

## 题量

- ecommerce：12 组，组号 `M1E01`–`M1E12`
- chinook：8 组，组号 `M1C01`–`M1C08`
- sakila：8 组，组号 `M1S01`–`M1S08`
- 每组 3 轮或 4 轮，各轮的题号是组号加轮次：`M1E01-1`、`M1E01-2`……
- 陷阱轮（见下）：ecommerce 2 轮，chinook 1 轮，sakila 1 轮
- 话题尽量分散：每个库各组的参考 SQL 合起来，ecommerce 至少覆盖 8 张表，chinook 至少 8 张，sakila 至少 10 张

## 一组追问长什么样

- **第 1 轮**是一个完整的问题，单看这一句就能回答。难度中等即可——这一套的重点在后面几轮
- **第 2 轮起是追问**：单看这一句答不了，或者会答成别的意思，必须结合前面的问答才知道问的是什么。
  像真实的人在对话里接着问：简短、口语化，不把前面的内容整段复述一遍
- **每一轮追问都要去库里查新的东西**，不能只靠前面已经给出的结果就答出来。例如上一轮列出了每家店的销售额，
  再问"其中哪家最高"就不行（看一眼上一轮的结果就知道）；问"那它们的退款呢"可以
- 一组里的话题要连贯，像同一个人顺着一条线往下问

追问的形式，在每一轮追问的 `tags` 里用 `追问:` 标出，一轮可以标几个：

- `追问:指代`：用"它们、这几家、他、其中、那个……"指前面答案里的对象
- `追问:省略`：只说变了的那部分，其余沿用上一问（"那 6 月呢""换成按城市看""北京的呢"）
- `追问:加条件`：在上一问的基础上收窄范围
- `追问:换角度`：对象不变，换一个指标，或者换一种分组
- `追问:跨轮`：指的不是上一轮，而是更早的某一轮；或者把前面两轮的东西放在一起问
- `追问:依赖结果`：不知道前面答案的具体内容，就写不出这一轮的 SQL（例如"排第一的那个客户，他都买过哪些类目"）

**分布**：每个库里每种形式至少出现 2 次（ecommerce 至少 3 次）；每一组的追问里至少用到两种形式；
每个库至少 2 组带 `追问:跨轮`。

## 陷阱轮

某一轮追问（结合上下文看）问的是库里根本没有数据能回答的东西。系统的正确行为是说明缺失，而不是编一个答案。

- 不能是第 1 轮。陷阱轮后面如果还有轮，下一轮要指回更早的、有答案的那一轮（这一轮同时标 `追问:跨轮`）
- `reference_sql="SELECT 1 WHERE 0"`、`must_hit_columns=[]`、`expect_unanswerable=True`，`tags` 里带 `陷阱题`
- 避开数据字典里已经写明"答不了"的主题

## 让每一轮都可判分

1. **参考 SQL 自包含**：每一轮的参考 SQL 在对应的库上单独就能执行，不依赖前面几轮；它表达的是"结合前面的
   问答，这一轮真正问的是什么"。可以把前面答案里的具体值写进去，也可以用子查询重新算出来，两种写法结果必须一致
2. **在上下文里答案唯一**：一个读过前面全部问答（包括前面几轮的正确答案）、只看数据字典的业务人员，应该能据此
   写出唯一正确的结果。"它们"可能指两样东西、"那上个月呢"不知道沿用哪些条件，这类情况要避免。
   口径（算哪些状态、日期区间两头算不算、按什么去重、"最近一次"按哪个时间）在第一次涉及的那一轮用自然的话交代清楚，
   后面的轮沿用。拿不准有没有第二种理解时，写进这一轮的 `note`，开头标"【存疑】"
   - 例外：数据字典里写明了口径约定的说法（ecommerce 的 `fact_order` 表描述里有一段「口径约定」），题面可以不再交代，
     参考 SQL 严格按约定写
3. **被指的对象少而明确**：后面的轮要指前面答案里的一批对象时，被指的那一轮结果控制在 10 行以内，就像人说"这几家"时那样
4. **输出列清楚**：可以自然地说，但要能看出这一轮返回哪几列
5. **TopN 无并列**：问前 N 名时，第 N 名和第 N+1 名不能并列；被后面的轮指代的前 N 名尤其要注意
6. **答案不退化**：结果不能是 0 行，也不能是单个 0 或 NULL
7. **枚举取值用原文**：问题里出现的枚举取值，必须是库里的原文
8. **小数位写明**：需要保留小数的，在这一轮的问题里写明保留几位，参考 SQL 里用 ROUND
9. **行序**：结果比对默认不看行序。只有这一轮明确要求排序、且排序没有歧义时，才设 `ordered=True`
10. **不写实现提示**：每一轮都不出现表名、字段名，不写"按某字段求和""关联某表"这类提示，也不写计算公式

## 字段怎么填（见 `evalcase.py`）

- 一组追问是一个 `MultiTurnCase`：`id`（组号）、`turns`（按顺序的各轮）、`tags`（这一组的难度：`难度:简单` /
  `难度:中等` / `难度:难`）、`note`（这一组顺着什么线索问、主要考什么）
- 每一轮是一个 `EvalCase`：
  - `id`：组号加轮次，如 `M1E01-2`
  - `query`：用户这一轮实际说的话，带着它的指代、省略
  - `reference_sql`：这一轮的正确答案，见上面第 1 条
  - `must_hit_columns`：这一轮答对必须用到的字段，写成 `"表名.字段名"`。几条路径同样正确时写成候选列表
    `["表A.字段", "表B.字段"]`，命中任意一个即可——前提是你验证过每条路径的结果完全一致
  - `tags`：第 2 轮起写 `追问:` 形式；陷阱轮带 `陷阱题`
  - `note`：这一轮在上下文里指的是什么、为什么答案唯一
  - `ordered`、`expect_unanswerable`

## 交付

1. 写进本目录的 `cases_multiturn1.py`：三个列表 `MULTITURN1_ECOMMERCE_CASES`、`MULTITURN1_CHINOOK_CASES`、
   `MULTITURN1_SAKILA_CASES`，用 `from evalcase import EvalCase, MultiTurnCase` 导入数据结构
2. 自己做一遍校验：每一轮的参考 SQL 在对应的库上跑通、结果不退化、TopN 不并列、必中字段真实存在；
   再把每一轮追问单独拿出来读一遍，确认它确实离不开上下文，也确实要去库里查新的东西。
   有候选路径的轮，把你验证用的其他路径的 SQL 写进本目录的 `alt_sql.json`（轮的题号 → SQL 列表）
3. 最不放心的轮，在它的 `note` 开头加"【存疑】"并写明原因
4. **最后的回复里不要写任何题目内容**——问题、SQL、字段、口径都不要写。只报告：文件路径、各库的组数和轮数、
   陷阱轮数、各追问形式出现的次数、存疑的题号、你遵守上面限制的情况，以及任何例外（包括会话环境里自动带的信息）
